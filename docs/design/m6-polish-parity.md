## Recipe-viewer integration (JEI / REI / EMI)

All three recipe viewers are supported, not REI alone — each is independently optional at runtime, and a player only ever has some subset installed. Recipe-fill from any of the three into crafting-terminal requests (M4), and warehouse-terminal search (M3) surfaced through each viewer's own usage/working-station hooks, same feature set across all three.

Dependency shape differs per viewer, confirmed against MC 1.21.1:

- **REI** (`me.shedaniel:RoughlyEnoughItems-api`, pinned to `16.0.788` to match Archie's own `modApi` dependency exactly — a second, differently-versioned copy on the classpath is asking for trouble): already resolves transitively via Archie's published POM, but `build.gradle.kts` needs its own explicit `modCompileOnly` declaration in `common` regardless — relying on a transitive compile-time dependency nobody explicitly declared is fragile the moment Archie's own dependency graph shifts. Its API is loader-agnostic, so both the plugin class and its registration can live in `common` — only the actual `REIClientPlugin` service-loader discovery (a loader-level hook Architectury doesn't unify) needs a one-line registration shim per loader (`fabric`'s own `rei_client` entrypoint, `neoforge`'s `META-INF/services` entry) pointing at the common plugin class.
- **JEI** (`mezz.jei:jei-1.21.1-common-api`, version `19.44.0.413`): also ships a genuine shared loader-agnostic api artifact, same shape as REI's — `mezz.jei.api.IModPlugin` and every registration interface it takes live entirely in this one artifact, not split per loader the way an earlier pass through this doc assumed. Discovery genuinely differs per loader, though - an earlier pass through this doc wrongly concluded neither loader needs a shim, based on the `@JeiPlugin` annotation's own generic Javadoc rather than either loader's real discovery source, and that error went undetected until real runtime testing showed the plugin silently never loading on Fabric at all (no exception, no button, exactly EMI's own two-mechanism shape): NeoForge's `ForgePluginFinder` (confirmed against its real source) does ASM-scan every mod's classes for `@JeiPlugin` directly, matching the original assumption there, but Fabric's `FabricPluginFinder` (also confirmed against its real source) doesn't scan for the annotation at all - it looks up a plain Fabric entrypoint keyed `"jei_mod_plugin"` via `FabricLoader.getEntrypointContainers(...)`, so `fabric.mod.json` needs that entry pointing at the common plugin class, same shape as `"emi"`'s own entry below. `modLocalRuntime(libs.jei.fabric` `/neoforge)` per loader module is still needed for the real mod jar at local dev-test time. Needs a new `maven.blamejared.com` entry added to the root repo list.
- **EMI** (`dev.emi:emi-xplat-intermediary`, `:api` classifier, version `1.1.24+1.21.1`): its own main coordinates (`emi-fabric`/`emi-neoforge`) aren't loader-agnostic - confirmed by diffing both loaders' `:api` jars' class lists, 76 of 77-78 classes are identical, only the two loader-specific ingredient-wrapper classes (`FabricEmiStack` vs `NeoForgeEmiStack`/`NeoForgeEmiIngredient`) differ - but that shared 76-class core is *also* published on its own, as `emi-xplat-intermediary` (an earlier pass through this doc missed this and wrongly concluded EMI needed real per-loader duplication). Same shape as Archie's own published modules: an intermediary-mapped artifact Architectury Loom remaps to whichever real platform is building, so `BoilerplateEmiPlugin` lives in `common` too, no different from REI's/JEI's. Discovery still genuinely differs per loader, though: Fabric needs the `"emi"` entrypoint in `fabric.mod.json` (pointing at the common class); NeoForge's own annotation scanning looks for `@EmiEntrypoint` directly on the class instead, which is safe to leave on unconditionally - neither loader's own EMI implementation scans for the other's mechanism. Already on `maven.terraformersmc.com` (already in the root repo list).

Shared, loader-independent logic (resolving a `Pattern`/`CraftingRequest` into whatever ingredient/result stacks a recipe display needs) stays in `common` as plain functions every plugin calls into.

Each of the three must runtime-guard on its own actual presence — none of the three is a hard dependency, and a player may have any combination of them (including none) installed. All three's own discovery mechanisms (REI's service-loader/entrypoint, JEI's `@JeiPlugin` annotation scan, EMI's entrypoint/`@EmiEntrypoint` pair) never load the plugin class at all unless the real mod is present, so none of them need an extra guard.

### Recipe-fill also pulls from storage and the terminal's own inbox

Each viewer's own "transfer recipe" click only ever fills the Crafting Terminal's grid from the player's carried inventory by default - the terminal itself sits on the pipe network, so it can do better. Each plugin wraps its viewer's own (otherwise unmodified) fill logic: it works out which real grid cell (0-8) each ingredient belongs in - REI via `SimpleGridMenuDisplay.getWidth()` converting the recipe's own (narrower) row-major index into a grid-relative one, JEI via `IRecipeTransferHandlerHelper.getGuiSlotIndexToIngredientMap` (already grid-relative), EMI via `EmiRecipe.getInputs()`'s own list index directly (`EmiCraftingRecipe` already stores it row-major against a 3-wide grid) - and, on a genuine committed action only, fires `CraftingTerminalHookMenu.requestIngredientSupply` with that `Map<Int, ItemResource>`. Getting a position slightly wrong here is harmless: vanilla's own shaped-recipe matching tries every valid offset itself, and each viewer's own (untouched) fill logic still re-derives the *actual* correct placement afterward from wherever the ingredient ends up - this step only has to make it reachable, not perfectly positioned.

**The request must never fire from a passive preview.** All three viewers evaluate a recipe's fill button far more often than a player ever clicks it - REI/JEI both run an explicit dry-run pass (`TransferHandler.Context.isActuallyCrafting() == false`, `doTransfer == false`) to decide the button's own enabled/tooltip state, and EMI's own `canCraft` is polled every frame a recipe view is open. Requesting supply from any of those would silently pull real stock (and animate a ghost item through the pipe) just from the player looking at a recipe, never clicking anything - REI/JEI gate the request on `isActuallyCrafting()`/`doTransfer` respectively; their own delegate re-verifies sufficiency independently on both the dry run and the real call, so gating only the *request* doesn't risk starving the real commit.

EMI has no such delegate to lean on: its `canCraft`/`craft` pair is a genuine check-then-trust contract - `performFill` never calls `craft` unless `canCraft` already returned `true`, and `craft`'s own default fill-then-consume logic (`EmiRecipeFiller.getStacks`) trusts that answer rather than blindly re-deriving it from scratch. An honest `canCraft` (nothing reachable without a request) would permanently starve `craft` of a chance to run at all. The fix keeps both calls honest without ever mutating from either: the outer `canCraft` optimistically reports `true` when every needed ingredient shows up in `CraftingTerminalHookMenu.results` (the terminal's own already-synced "what's reachable" snapshot - a pure read, no request, no server round trip) even if it isn't sitting in a real slot yet, just to get a click through to `craft` at all; `craft` then re-checks `StandardRecipeHandler`'s own default `canCraft` freshly (the real, quantity-aware `EmiPlayerInventory.canCraft` check) and only delegates to the real fill-then-consume logic once *that* genuinely agrees - a still-missing ingredient instead fires the real supply request and reports failure for that click. Second click succeeds once the supply has landed and synced back.

**The crafting grid must never be listed as its own ingredient source.** All three plugins originally declared their "pull ingredients from here" slot range as spanning the terminal's inbox through the player's inventory, which - since the grid sits physically between those two on the menu - included the grid itself, on the reasoning that a grid starting every transfer empty made the overlap harmless. That reasoning breaks the moment the grid can be pre-populated before a fill runs (a prior `supplyIngredients` grant, or simply a partially-assembled recipe the player left there): EMI's own default `craft` (`EmiRecipeFiller.clientFill`, confirmed against its real source) unconditionally clears every crafting slot first - a genuine simulated `ClickType.THROW` click, ejecting whatever's there - before refilling, and its own refill step explicitly refuses to treat a crafting slot as its own source (`if (slots.contains(input)) continue`), so anything sitting in the grid beforehand gets thrown away with no way to put it back from itself; if nothing spare exists elsewhere the fill just fails, with the original contents already gone. JEI's equivalent (`RecipeTransferUtil.validateSlots`, also confirmed against its real source) hard-rejects any overlap between "inventory" and "crafting" slots outright, meaning the JEI integration was silently failing validation on every transfer rather than voiding anything. Both viewers already have their own correct mechanism for "the grid already holds some or all of what's needed" - EMI's `EmiRecipeFiller.batchesAlreadyPresent`, JEI's `BasicRecipeTransferHandler.getInventoryState` folding a crafting slot's existing contents into its own available pool - so the grid never needed to be listed as a source to begin with. Every plugin now declares its source range as strictly `outputSlots + inventorySlots`, the grid excluded; for JEI this meant hand-writing an `IRecipeTransferInfo` instead of the single-contiguous-range `createBasicRecipeTransferInfo` convenience, since output/grid/inventory are no longer one contiguous span once the grid is cut out of the middle.

Server-side (`CraftingTerminalHookMenu.supplyIngredients`), for each targeted cell the player doesn't already carry and the terminal's own inbox (`TerminalHookState.output`) doesn't already hold: asks the network for it via the plain `RequestFulfillment.request`, landing in this terminal's own inbox exactly like a normal Store-tab withdrawal - a provider-hook pull still travels the real pipe distance, and a warehouse retrieval still queues its own real, pressure-gated gantry job. Either way this needs at least one more click once it's actually arrived, the same as any other shortfall.

`supplyIngredients`' own `amount` parameter (`RequestIngredientSupplyPacket.amount`) is the requested quantity per ingredient, capped at each resource's own max stack size regardless of what's asked. EMI's `EmiCraftContext.amount` is threaded straight through unchanged - `1` for a plain fill, `Int.MAX_VALUE` for a shift-click ("fill with as much as possible"), but also whatever exact count EMI's own BOM sidebar fill (recipe-tree mode) asks for when it fills the crafting table for one specific step of a larger tree, genuinely not always 1 or "as much as possible." REI/JEI only expose a boolean "shift-click fills as much as possible" signal (`TransferHandler.Context.isStackedCrafting()`, `maxTransfer`), so their own callers just map that to `1` or `Int.MAX_VALUE.toLong()` - relying on the same per-resource cap to bound the sentinel sensibly. Without a real quantity here, a shift-click fill would only ever request one unit per ingredient - enough for a single craft - leaving `CraftingTerminalHookMenu.craftOnce`'s own repeated-craft shortcut (`shiftClick`) to run dry again immediately even though the network could have supplied enough for several runs.

**No instant/synchronous grant.** An earlier version of this feature added `RequestFulfillment.requestInstant` - a reachable provider hook would deliver synchronously, decoupling "when the resource is logically available" from "when its visual travels through the pipe" (a purely cosmetic "ghost" `TravelingItem` still animated the route for visual continuity). It went through two rounds of fixes chasing real item loss - first landing straight in the targeted grid cell (which every recipe-viewer's own fill logic clears and rebuilds from declared sources that deliberately exclude the grid, so anything landed there ahead of a real commit had no way back once cleared), then landing in the inbox instead once that was diagnosed. The instant path was still too failure-prone in practice to keep for now, so it - along with `TravelingItem.ghost` and `fulfillFromProvider`'s `grant` parameter - was removed entirely; every ingredient the network supplies, instant-capable provider or not, travels the pipe for real. Revisiting a genuinely safe instant/ghost mechanism is left for later, if it's worth the complexity.

### Recipe-fill highlights ingredients by what it would take to get them

Each viewer's own default "missing ingredient" overlay paints every unavailable slot the same flat red - EMI's `StandardRecipeHandler.render`/`renderMissing`, REI's `SimpleTransferHandler.renderMissingInput`, JEI's internal (not part of the published api jar) `RecipeTransferErrorMissingSlots`. All three plugins override that default instead of layering on top of it, since the terminal knows more than "missing": a still-missing ingredient renders orange when it shows up in `CraftingTerminalHookMenu.results` (this terminal's own already-synced reachable-storage snapshot - a request would actually fetch it), blue when it shows up in `CraftingTerminalHookMenu.craftableResources` instead (a known pattern exists somewhere reachable, tying into the Pattern Provider network from M4), and only falls back to the original red when neither applies - genuinely not obtainable right now, by any means the terminal knows about. Orange is checked before blue when both would apply, since fetching existing stock is a simpler action than kicking off a whole crafting job.

**Every obtainability check considers every alternative a slot could accept, not one fixed representative.** A tag-backed ingredient (any plank color, say) has several possible matching items, not one - `targetsOf`'s own per-plugin mapping picks a single representative per grid cell for `requestIngredientSupply` itself (fine, since a request has to name one concrete item), but that same single value was also being reused for every "is this obtainable" check, which is wrong: it means a cell could look permanently unreachable while a *different* alternative the player already had sat right there for the same cell. First caught on JEI specifically - `IRecipeSlotView.getDisplayedItemStack()` cycles which single alternative it reports every few seconds, so the button would only become clickable once that cycle happened to land on whichever specific item the player actually had - but the same bug existed on REI and EMI too, just without the time-varying symptom (`targetsOf`'s own `firstOrNull` always picks the same one). Fixed by checking every alternative a slot's own ingredient reports (`IRecipeSlotView.getItemStacks()` on JEI, each `EntryIngredient`'s own full stack list on REI, `EmiIngredient.getEmiStacks()` on EMI) wherever a check decides obtainability, keeping `targetsOf`'s single-representative map only for the actual request.

JEI needed the most work here: `IRecipeTransferHandler.transferRecipe`'s own default delegate returns an opaque `IRecipeTransferError` with no way to tell *which* error it is or recolor it, so the plugin independently recomputes which `IRecipeSlotView`s are still unsatisfied (menu's own accessible slots, grid included) and substitutes a small `MissingIngredientError` (implementing the public `IRecipeTransferError`/`IRecipeSlotView.drawHighlight` directly, since the internal error class isn't available to depend on) whenever that list is non-empty.

**REI and JEI both tie the fill button's own clickability to the same dry-run check the coloring comes from - and that check has no concept of "reachable via network" either, the exact same problem `BoilerplateEmiPlugin.canCraft` solves for EMI.** Confirmed against real source in both cases: REI's `AutoCraftingEvaluator.evaluateAutoCrafting` calls `setEnabled(result.successful)` on the "+" button using a preview `handle()` call (`isActuallyCrafting = false`); JEI's `IRecipeTransferError.Type.USER_FACING` (what `createUserErrorForMissingSlots`/the delegate's own error always returns) has `allowsTransfer = false`. Neither default check knows the terminal could go fetch a missing ingredient, so the button stayed permanently disabled the instant any ingredient needed the network - a real click could never happen to trigger the request in the first place.

Fixed the same way for both, deliberately only counting `results` (network-reachable) toward "let the click through," not `craftableResources` (pattern-craftable) - a pattern existing doesn't mean `requestIngredientSupply` can fulfill it; that's the separate, deferred autocraft feature. REI's `handle` returns `TransferHandler.Result.createSuccessful()` for the preview call whenever every target is local or reachable, with a hand-built `TransferHandlerRenderer` manually attached so the tri-color highlight still shows even though the result itself is now "successful" (REI's own default renderer is only ever attached to a *failed* result). JEI's `MissingIngredientError.getType()` returns `IRecipeTransferError.Type.COSMETIC` instead of `USER_FACING` under the same condition - documented for exactly this purpose ("the button is active and can be used" while still showing the error/highlight on hover), no renderer juggling needed there.

A from-scratch, AE2/RS-style "ctrl-click to autocraft anything missing via a known pattern" was considered and deliberately deferred - out of scope for the recipe-*fill* feature itself, since it would mean bridging into the pattern-resolution/Crafting-CPU job system (`CraftingRequest.resolve`/`submitCraft`) directly from a recipe-viewer click rather than the terminal's own grid, a genuinely separate feature.

### Reserved-slot placeholders for in-flight deliveries

Every terminal request - a Store-tab withdrawal (`AbstractTerminalHookMenu.withdraw`) or a recipe-viewer supply pull (`CraftingTerminalHookMenu.supplyIngredients`) alike - travels a real pipe distance (or a real, pressure-gated gantry job) rather than landing instantly (see the no-instant-grant note above), so there's a real gap between "requested" and "physically in the inbox." Left entirely invisible, that gap reads as the request having silently failed. `PendingDelivery` (`id`, `slot`, `resource`, `amount`, `startTick`, `totalTicks`) fills it: a reservation is created the instant `RequestFulfillment.request`'s own `onDispatch` callback confirms a source actually exists (never for a request that finds nothing to pull from), stored on `TerminalHookState.pendingDeliveries`, and rendered client-side as a placeholder over the output slot it claimed - the *real* slot stays empty the whole time, deliberately, so a recipe viewer polling "is this ingredient here yet" gets an honest answer rather than a stack that isn't really there yet.

**A reservation is a genuine claim on one specific inbox slot, not just a place to draw a ghost.** `TerminalHookState.reserveOutputSlot` hands out the lowest slot that's both empty and unclaimed, along with what that slot can hold for the resource in question; the delivery lands in that exact index on arrival (`PipeBlockEntity.tick` inserting via `output.insert(slot, ...)` rather than a whole-storage insert), and `ReservedSlotStorage` - what `TerminalHookState.exposedItemStorage` now hands the *network* - refuses insertion into a claimed slot for everyone else in the meantime. That last part matters because a terminal inbox is a `FallbackItemStorageExposer`, which makes it a perfectly ordinary "any taker" destination for an unrelated extractor push (`PipeRouter.findRoute`): without the block, such a push could take a slot a still-in-flight withdrawal had already been promised, leaving that withdrawal to arrive with nowhere to go. The reserved delivery's own arrival deliberately bypasses that view and writes straight to `output`, since the block belongs on the shared surface, not on the slot itself.

This also makes over-requesting impossible by construction rather than by after-the-fact handling: every dispatch is capped to a single slot's real capacity, and `withdraw` splits a larger withdrawal across as many slots as the inbox can genuinely spare, stopping the moment it can't reserve another. Asking for more than the inbox can hold withdraws exactly what fits and leaves the rest in storage; `supplyIngredients` likewise skips (rather than fetches) any ingredient it can't get a slot for. Nothing is ever dispatched toward an inbox with no room for it, which is what previously left deliveries stalled at the destination retrying forever with a placeholder that never resolved.

`totalTicks` is a real estimate, not a flat guess: a provider-hook pull already knows its own real pipe route length (`route.size / PipeBlockEntity.SEGMENT_SPEED`); a warehouse retrieval combines its own gantry leg (`WarehouseControllerBlockEntity.estimateRetrieveTicks`, using the controller's current pressure-gated `effectiveGantrySpeed()` for the round trip to the rack slot and back) with the real pipe leg it still has to travel once it ships back out (`PipeRouter.findRouteTo`'s own hop count at the same fixed `SEGMENT_SPEED`) - genuinely accounting for both halves of the trip, though still approximate since gantry speed can change before the job actually runs.

Cancellation is a client click on the placeholder (`CancelPendingDeliveryPacket`) that just removes the `PendingDelivery` server-side - deliberately not an attempt to interrupt the `TravelingItem`/gantry job already in motion, which would mean reaching into two independently-ticking systems mid-flight for a purely cosmetic feature. Instead, `PipeBlockEntity.tick`'s own final-hop delivery check (`reservationOwnerAt`) looks up whether a `reservationId`-tagged item's reservation is still active the moment it actually arrives; a cancelled (or otherwise gone) one gets `redirectCancelled` - the exact same push-model search (`PipeRouter.findRoute`, excluding the terminal that just refused it) an ordinary extractor uses to find *any* taker - rather than landing anyway or vanishing. A delivery cancelled after a warehouse's gantry has already physically retrieved it still gets shipped out and still redirects correctly on arrival; the only cost is the wasted gantry trip, not a lost or duplicated item.

Client sync is poll-based, matching the Jobs tab's own tree poll (`RequestCraftJobTreePacket`, every 250ms) rather than a push on every server-side mutation: `RequestPendingDeliveriesPacket`/`PendingDeliveriesPacket` round-trip while the main tab is open, since an arrival or a cancellation has no other route to the client. Rendering (`PendingDeliveryOverlay`) draws three layers every frame, all computed straight from synced state rather than needing per-frame recomposition: a fake item icon, a countdown wipe using the *exact* draw call vanilla's own per-`Item` cooldown overlay uses (`GuiGraphics.renderItemDecorations`'s own `fill(RenderType.guiOverlay(), ...)` shape, replicated directly since there's no real `ItemCooldowns` entry to hook into) driven by `startTick`/`totalTicks` against the client's own current tick instead, and a red hover highlight (vanilla's own `AbstractContainerScreen.renderSlotHighlight` gradient, just red instead of white) since hovering here means "click to cancel," not "click to pick up." Each `PendingDelivery` is assigned to the next genuinely-empty output slot, in order (`AbstractTerminalHookMenu.pendingDeliveryFor`) - a real item already sitting in an output slot never gets a placeholder drawn over it.

## Config screens

Config values are declared incrementally as each earlier milestone introduces them (extraction interval and pipe speed in M1, priority tiers in M2, warehouse volume cap and scan budget in M3, crafting DAG depth limits in M4, pressure costs/multiplier curve in M5) via Archie's `ConfigContainer`/`ConfigSpec`/`CategorySpec` — not deferred wholesale to this milestone. M6's actual job is exposing Archie's auto-generated config screen (cloth-config-backed, per `../../AGENTS.md`'s Archie/cloth-config dependency note) through the mod's own UI entrypoint, not authoring the config values themselves.

## Wireless/remote terminal

`WirelessTerminalItem` using `ComposeItemContainerMenu<T>` (the item-backed analogue of `ComposeBlockContainerMenu`), NBT-bound via `NBTHolder.item(stack)`. Same search/withdraw/craft UI as the block terminal (M3/M4), gated by a small on-item `ArchieEnergyStorage` "charge" consumed per use — ties back into M5's pressure system for both theme and balance consistency (charging the terminal draws from the pressure network, same as everything else).

## VFX/SFX

Steam-puff particles and hiss/clank sounds triggered from tick hooks that already exist by this point (pipe hop from M1, gantry move from M3, pressure consumption from M5) via standard `ADeferredRegistryHolder<ParticleType<*>>`/`ADeferredRegistryHolder<SoundEvent>` registries — decoration layered onto hooks that already exist, not new plumbing.
