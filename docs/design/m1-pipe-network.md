# M1 — Pipe Network Core

See [README.md](README.md) for the shared registry/CSL-adapter/GUI/`PressureConsumer` conventions this builds on.

## Blocks & block entities

- **`PipeBlock`** — the lean, common case: six boolean connection `BooleanProperty`s (vanilla fence/pane-style dynamic `VoxelShape`), auto-connects to neighboring pipes and to any block exposing `ItemApi.BLOCK` storage. Carries no hooks and no hook-related storage.
- **`HookBlock : PipeBlock`** — a pipe segment that can additionally carry hooks. Kept as its own block/entity pair rather than folded onto every pipe: hooks bring six always-allocated 9-slot filter grids plus a synced map that a plain pipe (the overwhelming majority of a build) shouldn't pay for. A plain `PipeBlock` **promotes** into a `HookBlock` in place the moment a hook first attaches to it (see Placement below) - implementing and generalizing [decision #1](README.md#resolved-architectural-decisions) ("a plain pipe is upgraded in place, not swapped for a different block") to per-face rather than whole-block.
- **`PipeBlockEntity : NBTBlockEntity`** (base, backs `PipeBlock`):
  ```kotlin
  open class PipeBlockEntity(type: BlockEntityType<*>, pos: BlockPos, state: BlockState) : NBTBlockEntity(type, pos, state), PressureConsumer {
      val travelingItems by listField(TravelingItem.serializer()) { emptyList() }
  }
  ```
- **`HookBlockEntity : PipeBlockEntity`** (backs `HookBlock`):
  ```kotlin
  class HookBlockEntity(pos: BlockPos, state: BlockState) : PipeBlockEntity(TileRegistry.Hook, pos, state), ExtendedMenuProvider {
      @Sync val hooks: NestedNBTHolderMap by nestedMapField { tag -> HookTypeRegistry.byId(ResourceLocation.parse(tag.getString("type")))!!.createState() }   // keyed by Direction.name
      var pipeBlockId: ResourceLocation by field(ResourceLocationSerializer) { NONE }
  }
  ```
  `pipeBlockId` remembers which pipe type this hook block was promoted from/placed as (or the `NONE` sentinel, if no pipe has been placed here yet) - see Placement and Rendering below.

### Hooks: attachments, not separate blocks

A `HookBlockEntity` carries zero or more **hooks** — one per face, each an attachment rather than a distinct block, so a single pipe segment can carry an extraction hook on one face and a sorting hook on another simultaneously. `PipeHookType` is the behavior for a *kind* of hook (extraction, sorting, and whatever M3+ adds - a valve, a gauge); each hook type owns its own self-contained `HookHolderState` subclass (`ExtractionHookState`, `SortingHookState`) rather than every kind sharing one flat shape - see [m2-sorting-routing.md](m2-sorting-routing.md#module-data) for the current field breakdown, and [Archie's `NBTHolder.nestedMapField`](README.md) below for how the map itself is declared.

- **Registry, not a hardcoded enum**: `PipeHookType` entries live in a genuine custom Minecraft registry (`boilerplate:pipe_hook_type`, declared via Archie's `RegistrarHelper` and populated via `HookTypeRegistry : ADeferredRegistryHolder<PipeHookType>`), synced to clients. A new hook kind - including an addon mod's own, under its own namespace - is just another registry entry (with its own `PipeHookType.createState()` result), not a new block/block-entity pair. `HookHolderState.type` is accordingly a full `ResourceLocation`, not a bare name assumed to live under `boilerplate`. Runtime lookup by id goes through `HookTypeRegistry.byId(ResourceLocation)`, which resolves via the live `Registrar.get(ResourceLocation)` rather than `ADeferredRegistryHolder`'s own bookkeeping `Map` - the latter is populated at `register()` call time regardless of whether the underlying custom registry has actually processed that registration yet, so it isn't reliable for a runtime lookup (confirmed the hard way: it returned null for every hook during M2 gametest work, silently no-op'ing every hook tick).
- **Nested, self-contained state**: `HookBlockEntity.hooks` is declared via Archie's `NBTHolder.nestedMapField(factory: (CompoundTag) -> NBTHolder)`, not `mapField` - each entry is its own independently `field()`-declared `NBTHolder` (a real `net.kernelpanicsoft.archie.serialization.NestedNBTHolderMap`, not a plain `Map`), rather than one shared kotlinx.serialization-compatible value type. `factory` reads a saved entry's own raw `type` tag directly (before any typed holder exists to read it through) to decide which concrete `HookHolderState` subclass to reconstruct - the same mechanism that lets the map hold heterogeneous entries (an `ExtractionHookState` on one face, a `SortingHookState` on another) at all. Structural changes (`getOrPut`/`remove`) mark the block entity dirty/resynced automatically; mutating an *existing* entry's own field in place (as `HookBlockEntity.tick`'s hook loop does) doesn't, so the loop calls `hooks.touch()` once afterward.
- **Placement**: `HookItem` is a `BlockItem` for `BlockRegistry.Hook`. Used against an existing `PipeBlock`/`HookBlock` face, it attaches instead of placing a new block: a plain `PipeBlock` promotes into a `HookBlock` first (`PipeBlock.useItemOn` transplants the old block entity's data via `NBTHolder.saveToTag`/`loadFromTag`, mirrors its connections, and records `pipeBlockId`), then delegates to `HookBlock.useItemOn`, which attaches to whichever face `armFor(...)` resolves the hit to (falling back to the raw `BlockHitResult.direction`), if that face doesn't already carry one. Used against empty space (or any other block), `HookItem.place` places a fresh `HookBlock` and attaches to the face touching whatever was clicked (`context.clickedFace.opposite`). Shift-right-click empty-handed on a hooked face removes it; empty-hand right-click otherwise opens that hook's GUI, if it has one (`PipeHookType.hasMenu`) - `HookBlock.useWithoutItem`.
  - **Hit-face resolution** (`PipeBlock.armFor`): `BlockHitResult.direction` is the literal geometric face normal, correct only if you click an arm's outward tip - clicking one of its (narrower-than-a-full-face) lateral sides reports that side's own direction instead. `armFor` resolves the hit point back to whichever connected arm's own shape it actually landed in. A click lands exactly on the clicked face's plane, i.e. exactly on one of the arm shape's own bounds - `AABB.contains` is exclusive on the *max* bound, so it silently rejects a hit on an arm's south/east/up-facing side while accepting one on its north/west/down-facing side; `armFor` checks both bounds inclusively (with a small epsilon for floating-point slop in the hit point) instead, so every side matches consistently.
- **Extraction hook (`ExtractionHookType`)** — the *only* self-initiating hook in the network: every `EXTRACTION_INTERVAL_TICKS` it simulate-extracts from the `ItemApi.BLOCK` storage on its own attached face only; on success spawns a `TravelingItem` into the network. Fixing the pull side to one specific face, rather than the old M1 design's "any adjacent inventory is a fair source," is what makes source and destination distinguishable at all: without it, a bare inventory on a different face that just received an item looks exactly as "extractable" as the real source on the hook's very next cycle, and the two oscillate the stack back and forth forever (caught as a genuine bug, not just a design smell, during M2 gametest work).
- **Sorting hook (`FilterHookType`)** — see [m2-sorting-routing.md](m2-sorting-routing.md).
- **Rendering**: `HookBlock.getRenderShape` is `RenderShape.INVISIBLE` - it contributes no baked-model geometry of its own, and `hook.json` is a harmless unused placeholder. `PipeHookBlockEntityRenderer` draws everything for a `HookBlockEntity` itself: the pipe body, as `pipeBlockId`'s own baked model (built from that pipe type's `defaultBlockState()` with the same connections, but with any hook-carrying direction's connection forced `false` so the hook covers that face instead of a bare arm clipping through it) via `ModelBlockRenderer.tesselateBlock`; then each attached hook, modeled once facing north and rotated onto its actual face (`PoseStack` rotation around the block center). This means a promoted pipe keeps looking like whatever pipe type it actually is (driven by that type's own blockstate/models, resolved dynamically), and a future second pipe type needs nothing renderer-side beyond its own blockstate/models - no delegation to that pipe type's own block entity renderer if it happens to register one, since none does today and synthesizing a throwaway block entity per hook block per frame just to ask isn't worth doing speculatively; the baked-model path above is where that would extend if it's ever needed. A hook's model id is a *convention*, not a lookup table: `mymod:extraction` (the hook type id) resolves to the `inventory` variant of `mymod:extraction_hook`'s baked item model - the same model already guaranteed to exist for that hook's `HookItem` icon (registered as `<hook type path>_hook`), rather than a standalone block model nothing is guaranteed to have baked. An addon's own hook type gets a working model reference for free as long as its item follows the naming convention. Currently placeholder cuboid geometry/flat-color textures, generated via `BoilerplateBlockStateProvider` - see the Datagen section below. `tesselateBlock` (not the deprecated flat `renderModel` overload) samples real per-face block/sky light and applies Minecraft's directional shading itself - the flat overload paints every quad with one uniform light value and no shading (reads as fullbright).
- **Hook presence is not blockstate** - `hooks` (block-entity data) is the only source of truth for which faces carry a hook; there's no `hook_<direction>` blockstate mirror. Nothing needs one: collision (`getShape`, inherited from `PipeBlock`) already covers a hooked face via its connection boolean alone (a hook only ever attaches where a connection already exists), and rendering reads `hooks` directly (see above) rather than through a blockstate-conditioned model.
- **Sync**: attaching/removing a hook (`HookBlock.useItemOn`/`useWithoutItem`, `HookItem.place`) explicitly calls `level.sendBlockUpdated(...)` after mutating `hooks` - the `NBTHolder` field's own `setChanged()` only marks the chunk dirty for saving, it never pushes a network resync, so without this a client's `hooks` (and the renderer reading it) never advances past whatever it was at the last chunk load.

## Item representation in flight

```kotlin
@Serializable
data class TravelingItem(
    val stack: SItemStack,     // Archie's @Contextual ItemStack typealias, backed by CodecSerializer(ItemStack.CODEC)
    val fromDirection: @Serializable(with = DirectionSerializer::class) Direction,
    var progress: Float = 0f,  // 0f..1f across the current pipe segment
    var path: List<SBlockPos> = emptyList(),
)
```

`SItemStack`/`SBlockPos` are Archie's own contextual-serializer typealiases (`net.kernelpanicsoft.archie.serialization.serializers`) — already wired into the format's `SerializersModule`, so no bespoke item-id/component encoding is needed. `DirectionSerializer` is a small local `KSerializer<Direction>` (Archie doesn't ship one) encoding the enum by name, the same pattern Archie's own `BlockHitResultSerializer` uses inline for its `side` field. At the storage layer, conversion to/from CSL's `ItemResource` (needed to call `CommonStorage<ItemResource>.insert`/`.extract`) happens via `ItemResource.of(stack)`/`resource.toStack(count)` at the point of insertion/extraction, not on `TravelingItem` itself.

## Tick model

Each `PipeBlockEntity` with a non-empty `travelingItems` list is an active ticker. Per server tick:

1. `progress += speed` (speed = config-driven ticks-per-segment × `onPressureTick` multiplier once M5 exists; v1 default ≈ 1 block/second).
2. At `progress >= 1f`:
   - Next hop is another pipe → move the item to that `PipeBlockEntity`'s list, `progress = 0f`.
   - Next hop is a resolved inventory endpoint → attempt `storage.insert(resource, amount, simulate = false)` via `ItemApi.BLOCK.find`.
3. On insertion failure (full/rejected): the item **stalls at `progress = 1f`** and retries insertion every subsequent tick — no backoff in v1 (flagged for playtesting). If the route becomes permanently invalid (target endpoint removed) and no alternate route exists, the item **jams**: eject as a dropped-item entity at the stalled pipe. Thematically appropriate (a jammed tube), and avoids items silently vanishing.

**Implementation note**: `travelingItems` is fetched exactly once per `tick()` call and mutated only through index-based `set`/`removeAt` (`TravelingItem.copy(...)` standing in for field mutation) — see [README.md](README.md#gotcha-archies-listfieldmapfieldfield-only-persist-through-structural-mutation) for why in-place field mutation and iterator-based removal don't persist against Archie's `listField`.

**Client sync**: server is authoritative. A lightweight `PipeContentsSyncPacket(pos, items: List<TravelingItemDto>)` is broadcast via `toNearPlayers` periodically (e.g. every 4 ticks, or immediately on a hop) rather than every tick; the client interpolates `progress` locally between syncs (same dead-reckoning idea as vanilla entity motion), avoiding a packet-per-item-per-tick cost.

## Pipe network graph

`PipeNetworkManager` — one instance per `ServerLevel` (`WeakHashMap`-cached, not a persisted `SavedData`) — owns `BlockPos → networkId` and `networkId → PipeNetwork`. State is derived entirely from currently-loaded pipes, populated via `ensureRegistered` called idempotently at the top of every pipe's own `tick()` (there's no dedicated "block entity now active" lifecycle hook to call it from instead), rather than from serialized graph data:

```kotlin
class PipeNetwork(val id: UUID) {
    val members: MutableSet<BlockPos> = hashSetOf()
    var version: Int = 0   // bumped on any topology or module change; routing cache key
}
```

- **Placement (merge)**: **union-find** (disjoint-set) over network ids — O(α(n)) per placement, checking the 6 neighbors' existing network ids and unioning them. Exactly right for "grows constantly, rarely shrinks."
- **Removal (possible split)**: union-find can't cheaply detect splits, so removal (`onRemoved`) marks the network dirty and schedules a **chunked BFS rebuild** spread across `TickEvent.SERVER_LEVEL_POST` calls (budget e.g. 500 blocks/tick, same pattern M3's warehouse scan uses) from each remaining neighbor, assigning fresh network ids to whichever connected components result. Avoids a full-network single-tick stall on large builds while staying simple to reason about — no incremental cut-vertex bookkeeping.

`onRemoved`'s own scheduled set (`rebuildRemaining`) is one shared pool across the *whole level*, not scoped per invalidation - two unrelated removals landing in the same pending batch before either's rebuild has fully drained union their former members together. Since `SERVER_LEVEL_POST` runs strictly *after* every loaded pipe's own `tick()` this same server tick (and so after its own `ensureRegistered` call already re-registered it the ordinary, boundary-respecting way), the rebuild has to both (a) skip anything `networkOf` already knows about rather than blindly reprocessing it, and (b) respect `isBoundaryEdge` in its own frontier expansion exactly like `ensureRegistered` does - otherwise its raw-adjacency-only flood-fill can stomp an already-correct assignment, or walk straight across a boundary (M2's `SubnetBoundary`, M5's `PressureNetworkBoundary`) that should never merge just because both sides happened to share one pending batch. Confirmed the hard way once hook attach/detach started invalidating network membership too (see `m2-sorting-routing.md`/`m5-pressure-power.md`), which made two invalidations landing in the same batch far more common than the occasional plain block removal this rebuild was originally written for.

## Routing (M1 = unweighted)

Not per-item Dijkstra. Each extraction hook's pull resolves a target via plain BFS from its pipe over live pipe blockstate (not `PipeNetwork.members` directly — the network object is only consulted for the routing-cache key), testing each pipe-adjacent inventory with a **simulated** insert (`simulate = true`) until one accepts. The inventory the hook is pulling *from* (its own attached face) is passed as an `exclude` position and never considered a candidate — without this, a source with room for more of the same item (the common case, right after extracting from it) routes the item straight back to itself, which re-extracts it next cycle and never actually delivers anything. Result is cached per `(networkId, network.version, resource, exclude)` and invalidated automatically whenever `version` changes. M2 upgrades the cache key and candidate selection to weighted priority + color without touching this BFS machinery — see [m2-sorting-routing.md](m2-sorting-routing.md).

Sync is skipped entirely for a pipe that's idle (no items, nothing hopped this tick) rather than pinging empty state on the 4-tick timer regardless — every placed pipe ticks, so unconditional periodic sync means every idle pipe on a build broadcasts nothing-happened packets forever.

## Pipe tiers: opaque vs. glass

`PipeBlock` declares two traits an alternate tier can override - both plain `Boolean`s, never a `net.minecraft.client.renderer.RenderType` or other client-only type, since `PipeBlock` itself loads on a dedicated server too:

- `showsTravelingItems` — whether this tier's contents are visible in transit at all.
- `isTranslucent` — whether this tier's body renders into the translucent buffer rather than solid.

`GlassPipeBlock : PipeBlock` sets both `true`; the plain (opaque) tier leaves both `false`. Mechanically identical to a plain pipe (same connection logic, shape, network participation - inherited unchanged); only its own `TileRegistry.GlassPipe` block entity type (`GlassPipeBlockEntity`, otherwise just a `PipeBlockEntity` with no fields of its own) and blockstate/models differ, registered translucent client-side via Architectury's `RenderTypeRegistry.register(RenderType.translucent(), GlassPipe)` (`BlockRegistry.initClient()`) and per-model `"render_type": "minecraft:translucent"` in `glass_pipe_core.json`/`glass_pipe_arm.json`. A second pipe type needing genuinely different behavior (not just visuals) is still just another `PipeBlock` subclass with its own blockstate/models - no hook-side changes needed, since `HookBlock`/`HookBlockEntity.pipeBlockId` and the renderer below are already generic over whatever `PipeBlock` a hook was promoted from.

## Network types

A pipe's `NetworkType` participation determines both which `AbstractPipeNetworkManager`(s) it registers into and which attachments may attach to it - one custom registry (`boilerplate:network_type`, `NetworkType`/`NetworkTypeRegistry` mirroring `PipeHookType`/`HookTypeRegistry`'s own shape: `abstract fun managerFor(level: ServerLevel): AbstractPipeNetworkManager<*>`), with two entries today (`Item` → `PipeNetworkManager`, `Pressure` → `PressurePipeNetworkManager`; see [m5-pressure-power.md](m5-pressure-power.md)). Every `PipeBlock` declares one **primary** type (`primaryNetworkType`, gates attachment compatibility) plus a set of **secondary** types it also conducts without gating attachments (`secondaryNetworkTypes`) - an item pipe's primary is `Item`, secondary `{Pressure}` (pressure has always flowed through the item network for free; this is that same behavior, now named). Every `PipeAttachmentType` (hook or encasement) declares `compatibleNetworkTypes`; `MultipartBlock.clickBlockWithItem` refuses to attach one whose set doesn't contain the segment's resolved primary type (a pipe-less segment, primary type unresolved, accepts anything - there's nothing to be incompatible with yet). `networkTypesAt`/`primaryNetworkTypeAt` (`pipe/network/NetworkTypeResolution.kt`) resolve a position's active set by reading the underlying `PipeBlock` directly, or (for a promoted `MultipartBlock`) whichever pipe type `MultipartBlockEntity.pipeBlockId` names - empty/`null` for a bare unpromoted segment. `PipeRouter.isPipe` is just `NetworkTypeRegistry.Item in networkTypesAt(...)`.

A dedicated pressure-only pipe (`PressurePipeBlock`, primary `Pressure`, no secondary) is otherwise just another `PipeBlock` subclass - same `MultipartBlock`/`MultipartBlockEntity` promotion path, narrower cross-section and `EnergyApi` external-connection probe instead of `ItemApi`. The one place `Item`-vs-`Pressure` primary types actually matters at the network-topology level: an item-pipe segment touching a dedicated pressure-pipe segment doesn't auto-merge into one pressure network on its own (unlike item-to-item or pressure-to-pressure edges, or an item pipe reaching straight into an `EnergyApi` neighbor) - see `PressureNetworkBoundary` in [m5-pressure-power.md](m5-pressure-power.md), which gates exactly that one junction behind an `AdapterHookType` hook, mirroring `SubnetBoundary`/`InterfaceHookType`'s existing item-network boundary mechanism below.

### Traveling items in flight

`TravelingItemRenderer` (a plain object, not tied to any block entity type) draws each `TravelingItem` as a small floating item, spinning slowly, moving in a straight line from the face it entered through (`fromDirection`) toward the face it's headed to next (`path.firstOrNull()`, resolved back to a `Direction`) - a straight lerp through a bend's corner rather than following the bend's own curve, an accepted simplification. Reads `PipeContentsClientCache`, not `PipeBlockEntity.travelingItems` directly (server-authoritative, never `@Sync`); `PipeContentsClientCache.get` dead-reckons `progress` forward by elapsed time since the last sync packet using the same `SEGMENT_SPEED`, so motion stays smooth between syncs instead of stepping every 4 ticks.

Two call sites share this, deliberately via composition rather than a common renderer base class - the shared piece (given a list of items and a position, draw them) is narrow and stateless, and the two renderers' surrounding responsibilities are otherwise unrelated (one draws nothing else at all, the other draws a pipe body and hooks):

- `TravelingItemBlockEntityRenderer` — registered only for `TileRegistry.GlassPipe`, so the cost never applies to a plain (opaque) pipe.
- `PipeHookBlockEntityRenderer` — additionally calls it (and picks the pipe-body buffer via `isTranslucent`) if the resolved `pipeBlockId` block's `showsTravelingItems`/`isTranslucent` say so, so a hook promoted from a glass pipe keeps showing its contents translucently and one promoted from an opaque pipe doesn't - the trait belongs to the pipe type, not to whether a hook happens to be attached. Hooks themselves always render solid on their own buffer regardless, being separate physical attachments rather than part of the tube.

## Datagen

`BoilerplateBlockStateProvider.boilerplateBlockStates()` generates every blockstate/block-model/item-model JSON under `assets/boilerplate` (`pipe`/`glass_pipe`/`hook`'s blockstates, `pipe_core`/`pipe_arm`/`glass_pipe_core`/`glass_pipe_arm`/`extraction_hook`/`sorting_hook`'s block models, and the four item models pointing at them) - hand-written JSON is gone. `BoilerplateDatagen : ADatagenEventObject` registers it, gated behind `ADataGeneratorPlatform.isDataGen` in `Boilerplate.init()` exactly like `BoilerplateGameTest`/`AGameTestPlatform.isGameTest` - `archie-datagen-common` is the same story as `archie-gametest-common`, a dev-only dependency absent from the production runtime classpath.

Output goes to `common/src/main/generated`, wired in as an extra resources root on `common`'s own sourceSet (`fabric`/`neoforge`'s existing `processResources { from(project(":boilerplate-common").sourceSets.main.get().resources) }` merge picks it up for free) - not `common/src/main/resources` directly, despite that being where the hand-written JSON used to live. Minecraft's datagen `CachedOutput` treats its entire output directory as exclusively its own and deletes anything in it a provider didn't just (re)write; pointing it straight at `src/main/resources` deleted the hand-placed textures and the gametest structure NBT sitting alongside the JSON on the first real run. `common/src/main/generated` is committed (a `.gitignore` exception carved out of the `**/src/main/generated` rule that's otherwise right for Archie, a library regenerated on demand by consumers) - unlike Archie, a Boilerplate checkout needs to build without a `runDatagen` step first. Regenerate with `./gradlew :boilerplate-fabric:runDatagen` (or the `neoforge` variant) after changing block/model logic, and commit the result.

## Deferred to playtesting / not blocking

- Stall/backpressure behavior tuning beyond "retry every tick, then jam."
- Further pipe tier speed/art (brass/copper/lead, speed-per-tier) beyond the opaque/glass split above.
- Routing only excludes the immediate extraction source, not general cycles elsewhere in the network (e.g. a loop that could route an item back to its origin via a different path) — not handled yet.
- Real hook/pipe models and textures — current geometry (a north-facing cuboid nub per hook, rotated in place; a multipart cuboid-arm pipe body) and flat-color textures are placeholders.
- Two Archie `@Sync` bugs found while building this, now fixed upstream in Archie: (1) `NBTHolder.mapField`/`listField` registered the wrong serializer for `@Sync` (element instead of collection), crashing on sync; (2) `BlockEntityStateContainer`'s reflective property scan used module-less, generics-erased `KClass.serializerOrNull()`, which can't resolve a `@Contextual`-annotated field at all.
- `hooks` is `@Sync`-annotated *and* explicitly resynced via `level.sendBlockUpdated(...)` at the point of mutation (see `HookBlock.useItemOn`/`useWithoutItem`, `HookItem.place`) - the latter is what every *nearby* client's own block entity copy actually needs, since that's what `PipeHookBlockEntityRenderer` reads. `@Sync` alone doesn't reach that, and - unlike a top-level `@Sync` field - a `nestedMapField`'s individual entries also aren't wired into `BlockEntityStateManager` for live GUI observation at all; `SortingHookScreen` reads its hook's state once when the screen opens instead, and pushes edits back via a dedicated `UpdateSortingRoutingPacket` C2S packet - see [m2-sorting-routing.md](m2-sorting-routing.md#gui).
