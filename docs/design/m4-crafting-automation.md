# M4 — Crafting Automation

See [README.md](README.md) for shared conventions and [m3-warehouse-storage.md](m3-warehouse-storage.md) for `WarehouseIndex`/the gantry job queue this builds on.

## Pattern representation

Built on vanilla recipes rather than inventing a new format: a `Pattern` is a snapshot taken at encode time (AE2-style pattern encoding, not a live `RecipeHolder<CraftingRecipe>` reference - a later game/recipe change should never retroactively invalidate an already-encoded pattern), or a manual input/output list for non-vanilla "processing" conversions:

```kotlin
data class Pattern(
    val inputs: List<SItemResource>,               // up to 9, one per grid cell for CRAFTING (positional), an unordered bag for PROCESSING
    val outputs: List<SResourceStack<SItemResource>>, // 1 for CRAFTING, up to 9 for PROCESSING
    val kind: PatternKind,                          // CRAFTING | PROCESSING
)
```

No separate per-input quantity field - a resource's own required count is just how many of the 9 `inputs` entries hold it (`Pattern.requiredInputs()`), the same "count via slot occupancy" shape a real crafting grid already has.

**Patterns are items, not block-owned state** - a `PatternItem` (one item type; blank or encoded is just its own stack-component data, the same way an empty vs. written book share one item type). `PatternItemData(stack)` gives it the same `field`/`itemField` delegate API a `BlockEntity` gets (`NBTHolder.item(stack)`, backed by the vanilla `CustomData` component); its one field, `pattern: Pattern?`, is backed by a private 0-or-1-element `List<Pattern>`, not a genuinely nullable field - knbt's `AbstractNbtEncoder` doesn't support `encodeNull` any more than it supports `encodeEnum` (the same latent gap `PatternKindSerializer` already works around below), so a real nullable serializer crashes the instant a stack goes back to blank. A pattern travels through pipes/inventories/warehouses like anything else, rather than living pinned to whichever block it was authored on.

`PatternEncoder.encode(level, kind, grid, patternOutputs)` snapshots a plain `ArchieItemStorage` grid/pattern-outputs pair into a `Pattern` of the *explicitly requested* `kind` - not auto-detected by whether the grid happens to match a real recipe. `PatternKind.CRAFTING` matches `grid` against `RecipeManager`/`CraftingRecipe.assemble` and snapshots the *actual assembled* result (`null` if nothing matches; `patternOutputs` unused); `PatternKind.PROCESSING` snapshots every non-empty slot of `patternOutputs` as-is, up to all 9, regardless of whether `grid` also happens to match a vanilla recipe (`null` if none are set). A no-op either way if `grid` itself is entirely empty. Kept as a standalone object, not inlined into any menu, so it's directly testable without a real menu/player - see `PatternEncoderGameTest`.

Caught the same latent knbt bug `FilterMode`/`RoutingModule` did (see `docs/design/m2-sorting-routing.md`): a plain enum's default `encodeEnum` isn't supported by knbt's encoder at all. `PatternKindSerializer` (encode/decode by name) fixes it the same way `FilterModeSerializer` does - confirmed by an actual crash on `PROCESSING` before the fix.

## Pattern Provider hook

A `PatternProviderHookType` hook (`providesItems = true`) holds up to 9 `PatternItem` stacks in its own slots and watches its attached face's target for a currently-held pattern's ingredients to appear - `tick()` scans its own held patterns each tick, checking the target's combined `get()`/`size()` view (not a directed `extract(simulate=true)`, which only reads a directed storage's *output* side - a real bug hit and fixed here, confirmed via revert-and-fail: a target like `AssemblyTableBlockEntity` has separate `grid`/`output` slots, and simulating an extract of *input* ingredients sitting in `grid` always reads as unavailable). Once a match is found, it calls `AssemblyTableBlockEntity.beginProcessing(pattern)` - a self-driving target (a vanilla furnace, say) needs no such trigger at all. The hook's own held patterns' outputs are exposed as pullable network stock through the *existing* provider-style pull machinery (`providesItems = true` is all that's needed - see `RequestFulfillment.ProviderSource`), reading the target's own output side once something's actually been produced.

This replaces "a table stores its own pattern list" outright - a table doesn't know its own recipes any more than a furnace does. `AssemblyTableBlockEntity` no longer owns a `patterns` list at all; it just exposes `activePattern: Pattern?` (private-set) and `beginProcessing(pattern): Boolean` (rejects if something's already running, or if `canRun(pattern)` fails against the grid's current contents right now).

`RequestFulfillment.reachablePatternProviders(level, from)` returns `PatternProviderSource(hookPos, direction, state)` for every reachable `PatternProviderHookType` hook - the crafting resolver's and the terminal's own entry point for "what can produce X" (see "Resolution"/"Terminal" below), replacing the old `reachableAssemblyTables`.

## Physical Assembly Table

[Decision #4](README.md#resolved-architectural-decisions): a real `AssemblyTableBlockEntity` that pipes feed and which visibly processes crafts over time, rather than resolving instantly once inputs are satisfied. Fits the mailroom/industrial-process theme, and gives M5's pressure mechanic something concrete to gate via the `PressureConsumer` hook (`basePressureCost`/`onPressureTick` scale how fast a craft completes — see [m5-pressure-power.md](m5-pressure-power.md)).

`tick()` only progresses `activePattern` if one's running (re-checking `canRun` every tick rather than caching it - an ingredient pulled back out mid-run genuinely aborts progress, `progressTicks` resetting to `0` the moment nothing matches). Once `beginProcessing` starts a run, `progressTicks` accumulates `onPressureTick(NO_PRESSURE_LINE)` (a stand-in energy line until M5, so this is presently a flat `1.0`/tick) each tick; at `PROCESSING_TIME_TICKS` (100, ~5 seconds at 1.0x) it consumes the inputs and produces the outputs and clears `activePattern`. Confirmed genuinely gated (not instant) via a gametest that reverted the tick-budget check and watched it fail.

`grid`/`output` are one shared slot pair, reached through `ioStorage`, a small `CommonStorage<ItemResource>` wrapper that routes `insert` to `grid` and `extract` to `output` regardless of which slot index a call touches (`get`/`size` still expose both combined, for generic introspection), exposed via `exposeRackStorage` (the same helper the rack block types use — generic over any `CommonStorage`, not rack-specific).

## Resolution

`CraftingResolver.resolve(target, amount, stockOf, patternFor)` resolves into a **DAG**, not a tree — memoized per-resource within one resolution pass so, e.g., two branches both needing iron ingots share one sub-request rather than double-counting. `stockOf`/`patternFor` are plain functions, not tied to `WarehouseIndex`/`PatternProviderHookState` directly, so the algorithm itself is a pure, directly-testable unit; `CraftingRequest.resolve(level, from, target, amount)` is the real wiring, summing stock across every `WarehouseControllerBlockEntity` reachable from `from` and taking the first pattern match found across every reachable `PatternProviderHookState`'s own held patterns (`reachablePatternProviders(...).flatMap { it.state.heldPatterns() }`).

Turned out to need two passes, not one interleaved recursion - a shared resource's *total* demand (needed to decide how much actually has to come from stock vs. crafting) isn't known until every consumer of it has been discovered:

1. **Discover** - DFS from `target`, recording each resource touched in post-order (a resource's own pattern inputs are recorded before the resource itself); a resource reached while still in-progress further up the same branch fails fast as `Result.Cyclic`, rejecting an impossible/self-referential pattern chain cleanly instead of recursing forever.
2. **Demand** - walk that post-order **in reverse** (target first, deepest leaf ingredients last) accumulating each resource's total demand as its consumers are visited; by the time a resource itself is reached, every consumer that could ever add to its demand already has, since a consumer always sits earlier in the reversed order than what it consumes. A resource still short after stock is checked against its own pattern - `Result.Unresolvable` if it has neither.

The result (`CraftingResolver.Plan`) lists `steps` (one `CraftStep(pattern, runs, resource)` per pattern actually needed, in bottom-up order - a leaf ingredient's own craft always precedes whatever consumes its output; `resource` is the demand that sized `runs`) and `stockPulls` (total pulled directly from stock, per resource, across the whole plan). `CraftingResolver.maxCraftable(target, upperBound, stockOf, patternFor)` binary-searches over `resolve` itself for the largest amount still resolvable - see "Terminal" below.

## Terminal family

Three sibling hook types share one job queue and one Store-tab shape, each a near-duplicate menu/screen class rather than a real class hierarchy - `ComposeBlockContainerMenu`'s own self-referencing `SELF` type parameter makes real inheritance awkward, and every other hook type in this mod already accepts that tradeoff:

- **`TerminalHookType`** - the plain terminal: search/withdraw stock, browse/request autocrafts, view the job tree.
- **`CraftingTerminalHookType`** - everything the plain terminal does, plus a real 3x3 grid for instant, manual, real-item crafting.
- **`PatternTerminalHookType`** - everything the plain terminal does, plus a *ghost* grid for authoring patterns without needing the real items in hand.

All three inherit `TerminalHookState.jobs`/`.output` wholesale (`TerminalHookState` is `open`); `advanceTerminalJobs`/`advance` (the job-queue driver, see "Execution" below) are plain top-level functions in `TerminalHookType.kt`, not object methods, specifically so the other two can drive the exact same queue without needing real inheritance from a Kotlin `object`.

### Store tab

One tab, not a separate "Store" and "Craft" pair - `StoreResultsGrid` (`pipe/gui/StoreResultsGrid.kt`, shared across all three menu classes since it takes plain data/callbacks rather than a concrete menu type) merges current stock (`TerminalHookMenu.results`) and the craftable catalog (`TerminalHookMenu.craftableResources` - the distinct resources any reachable `PatternProviderHookState`'s own held patterns can produce) into one grid, filtered by a sidebar cycle button (`StoreViewMode`: Stock / Craft / All - the AE2-terminal-style toggle, cycling on click) instead of a dedicated autocraft-browsing tab:

- An entry with real stock (`amount > 0`) shows its real count; a plain click opens `requestQuantityDialog` and withdraws - unchanged from before.
- An entry with **no** stock but a matching pattern (`craftable = true`, `amount == 0`) shows `"Craft"` as its count text instead of a number, and a plain click opens `requestCraftQuantityDialog` directly - there's nothing to withdraw.
- An entry that's **both** in stock and craftable keeps the normal withdraw click; a **middle-click** additionally opens the autocraft dialog for it (`TerminalSlot`'s own `middleClickHandler`/`onMiddleClick`, the same mechanism `GhostSlot` already used for filter-card editing - detecting an actual middle click can't happen inside `Clickable` itself, since a `PointerEvent` doesn't carry which button triggered it, only `DragEvent` does; it's intercepted one level up, at the screen's own `mouseClicked` override).

A real, `Slots`-backed row of nine `"output"` slots sits underneath the grid either way - a withdrawal or finished crafting job delivers straight into the terminal's own `TerminalHookState.output`, not an external chest wired to some other face. `PipeBlockEntity.tick()`'s own hop-vs-deliver decision needed a small general fix for this to actually work: `val isFinalHop = item.path.size == 1` is now an additional bypass alongside the existing `SubnetBoundary`-specific one, since a route's own last waypoint should always deliver regardless of whether it happens to be pipe-shaped (a terminal's own position is) - previously only interface hooks had this carve-out, and a terminal's own delivery silently jammed without it.

- **Preview** - `requestCraftQuantityDialog`'s own quantity field re-sends `RequestCraftPreviewPacket(resource, amount)` on every change (a `LaunchedEffect`), and the server replies with `CraftPreviewPacket(resource, maxCraftable)` via `CraftingResolver.maxCraftable`. The dialog's "Craft" button stays disabled until `maxCraftable > 0`.
- **Request** - a bespoke client→server `CraftingRequestPacket(resource, amount)` - an *action*, not state, one of the few places this milestone needed a packet rather than reusing a search/preview round-trip shape.
- **Job status** - a plain `String` (`HookBlockEntity.craftJobStatus`), `@Sync`'d the ordinary NBT block-entity way - superseded for anything detailed by the Tree tab (below), but still the quick-glance summary.

### Crafting Terminal: instant, real-item crafting

No physical "Craft" button - the grid sits right under the Store tab's own output slots, and its result slot (`LiveResultSlot`, a `FakeSlot`, never a real vanilla `Slot`) mirrors a real vanilla crafting table exactly: a live, server-computed preview (`InstantCrafting.match`, polled via `RequestCraftGridPreviewPacket`/`CraftGridPreviewPacket` rather than derived client-side, matching every other dynamic value this menu surfaces), a plain click crafts once onto the cursor (refused - grid untouched - if the cursor already holds something incompatible, or would overflow its own max stack), and a shift-click quick-crafts repeatedly straight into the player's own inventory until the grid stops matching, the inventory has no room, or a `MAX_QUICK_CRAFT` (64) safety cap is hit. `InstantCrafting` (`crafting/InstantCrafting.kt`) is the standalone, directly-testable object behind both the preview and the actual craft - `CraftingTerminalHookMenu.craftOnce`/`sendGridPreview` are thin wiring over it, not where the logic lives.

### Pattern Terminal: authoring patterns without real items

Same grid position, but every cell is a *ghost* (`GhostSlot`/`GhostSlotGrid`, the same reference-only widget `SortingHookState.filter` already uses - left-click with an item held *copies* its identity in without consuming it, left-click an occupied cell empty-handed clears it). An explicit `RadioGroup` toggles `PatternTerminalHookState.patternKind` between the two `PatternKind`s, rather than `PatternEncoder` auto-detecting one from the grid:

- **Crafting** - the ghost input grid's positions matter, matched against a real recipe at encode time; a hint line, not a live preview, explains this (a live ghost-driven preview was judged not worth the added complexity here, unlike the Crafting Terminal's real-item one).
- **Processing** - the ghost inputs are an unordered bag (same as before), but the output side becomes its own 3x3 *ghost output* grid (`ghostOutputs`/`ghostOutputAmounts`, up to 9 distinct manually-specified outputs, each with its own amount) instead of one forced-single slot - `GhostSlot`/`GhostSlotGrid` grew an optional `amount`/`onAmountScroll` pair for this (display via `FakeSlot`'s existing count-badge parameter; adjusted by scrolling over an occupied cell, `+1`/`-1` per notch, clamped `1..64`).

A real, persistent `blankPatterns` slot (`Slots("blankPatterns", 1, 1)`) holds the stack of blank `PatternItem`s encoding draws from - not the player's own inventory, so the terminal itself can be pre-stocked and left alone. `PatternEncoder.encodeAndConsume(level, kind, grid, patternOutputs, blankPatterns, deliverTo)` is transactional: the blank is only actually consumed once a *simulated* insert into `deliverTo` (the terminal's own `output` slots) confirms there's room, so a full output row never silently eats a blank pattern for nothing. It consumes the blank via `ArchieItemSlot.remove` on the specific slot index, not `ArchieItemStorage.extract` by resource - see "Known gaps" below for why.

## Node-based crafting job tree (Tree tab)

A third tab, present on all three terminal types, replacing a plain status line with a real, pannable node graph of the front-of-queue `CraftingJob` - "kind of like the advancements menu," per its own design ask. `CraftingJob.toTree()` builds a `CraftJobTreeNode` (a plain, network-serializable recursive DTO: `resource`/`amount`/`status`/`done`/`children`) rooted at the step producing the job's own `target`, recursing into whichever of its own required inputs also has a step producing them - `CraftingJob.stepStatus(index)` derives each node's status text purely from the job's existing bookkeeping (`tableForStep`/`fedInputs`/`done`), no new persisted state needed. A resource needed by more than one consumer appears once *per consumer* rather than being deduplicated into a shared node - a plain tree, not a compacted DAG, given how small a job's own tree realistically gets; not worth a real graph-layout algorithm.

`RequestCraftJobTreePacket`/`CraftJobTreePacket` carry the tree to the client on request (the Tree tab polls it, same `LaunchedEffect` cadence as job-status polling), dispatched through a new `CraftTreeMenu` interface all three terminal menus implement - the same reason `CraftPreviewMenu` exists for the craft-preview slice of this same dispatch problem.

`PannableCanvas` (`pipe/gui/PannableCanvas.kt`) is a new, generic click-drag-panned, scissor-clipped viewport, built on the same `Layout`/`Renderer` primitives `Scrollable` uses (minus the scrollbar and lerp animation - a node graph pans 1:1 with the drag). `CraftingTreeView` lays a `CraftJobTreeNode` out over it column-per-depth (pre-order row assignment, not a compacted layout), connected by simple two-segment elbow connectors drawn directly via `GuiGraphics.fill`.

## Execution

Resolving a request (`CraftingRequest.resolve`) only produces a `CraftingResolver.Plan` - actually running it is `CraftingJob`, a purely in-memory (not NBT-persisted, like `TravelingItem`) object living on `TerminalHookState.jobs`, advanced one tick at a time by `advanceTerminalJobs`/`advance`:

- A target fully covered by existing stock (`plan.steps` empty) reduces to exactly the same `RequestFulfillment.request` call an ordinary withdrawal makes, delivering straight to the terminal's own position.
- Otherwise, each `CraftStep` is assigned the first reachable `PatternProviderHookState` holding a matching `Pattern` whose own target position no earlier step in the same job has already claimed, and its ingredients are requested (once each, tracked per `(step, resource)` pair) via `RequestFulfillment.request` targeting that target position directly.
- Once fed, the target's own processing (e.g. `AssemblyTableBlockEntity.tick`, once `beginProcessing` was triggered) runs on its own schedule. The job doesn't watch for that directly - it just retries pulling the *final* target to the terminal's own position every `PULL_INTERVAL_TICKS`, the same `RequestFulfillment.request` a plain withdrawal uses. That pull only succeeds once something makes the finished result actually reachable - the same `PatternProviderHookType`'s own `providesItems = true` exposure, or any other provider-style hook physically wired to it. A multi-step chain (one step's output feeding another's input) works the same way, through the player's own pipe wiring, with no special-casing.

Covered end-to-end by `TerminalCraftGameTest` (stock-only request, full single-step craft via a `PatternProviderHookType` hook feeding an `AssemblyTableBlockEntity`), `PatternProviderHookGameTest` (the hook's own reactive trigger behavior, both the positive case and "does nothing without matching ingredients"), and `CraftingJobGameTest` (`toTree`/`stepStatus` in isolation, against a hand-built job).

## Known gaps

- **`ArchieItemSlot.extract` unreliable for component-bearing items** - intermittently fails to match a stack carrying real `DataComponent` data (confirmed with a blank `PatternItem`'s own `CustomData` component) via `extract`'s own `resource.test(unit.toStack())` comparison, even when the exact same slot's `getItem()` reads back correctly moments earlier. Worked around in `PatternEncoder.encodeAndConsume` by consuming via `ArchieItemSlot.remove` on the known slot index instead (no resource-equality check involved at all); not fully root-caused. See `[[archie-itemslot-extract-by-resource-unreliable-for-component-items]]` memory.
- **A previously-crashing Archie bug, now fixed upstream**: `KOps$Nbt`'s own list-building helper (`net.kernelpanicsoft.archie.serialization.KOps`) force-unwrapped a `null` conversion result for a genuinely empty NBT list (`ListTag.fromMinecraft` intentionally returns `null` for an untyped/empty list - there's no vanilla tag-type byte to recover a type from), crashing `HookBlockEntity.tick()` on every tick a real item slot held a blank `PatternItem` (whose own `patternList` field is an empty list when blank). Fixed in Archie directly (special-cased the empty case), republished to `mavenLocal()`; `PatternTerminalHookGameTest.testBlankPatternInARealSlotSurvivesRepeatedTicking` is the regression test.
- **Terminal-family packets cast too narrow** - every packet shared across all three terminal menus (`RequestTerminalSearchResultsPacket`, `RequestCraftPreviewPacket`, `CraftPreviewPacket`, `CraftingRequestPacket`, `TerminalItemDepositRequestPacket`, `TerminalItemWithdrawRequestPacket`, `TerminalSearchResultsPacket`, `RequestWarehouseDefragPacket`, `CraftableListPacket`, `RequestCraftableListPacket`) casts `containerMenu` to the concrete `AbstractTerminalHookMenu` only, not a shared interface - a player with a `CraftingTerminalHookMenu`/`PatternTerminalHookMenu` open fails every one of those casts and the handler silently no-ops. `CraftJobTreePacket`/`RequestCraftJobTreePacket`/`CraftGridPreviewPacket`/`RequestCraftGridPreviewPacket` (added this milestone) got this right from the start via dedicated interfaces (`CraftTreeMenu`, concrete-type for the grid preview since it's Crafting-Terminal-only) - the older, pre-existing packets still need the same treatment. See `[[terminal-family-packets-cast-too-narrow]]` memory.
- A `CraftingJob`'s per-step pattern-provider target is picked once, greedily, and never reassigned - a target going offline (broken, or its patterns edited) mid-job stalls that job rather than re-resolving onto a different one.
- `RequesterHookType` has no in-flight-request tracking - a delivery slower than its own `REQUEST_INTERVAL_TICKS` can get double-requested. Predates this milestone; see `[[requester-hook-no-inflight-tracking]]` memory.
- Ingredient remainders (an emptied bucket, say) from `CraftingTerminalHookMenu`'s instant crafting aren't handled - the emptied container is simply discarded along with the rest of the consumed slot.
- EMI's recipe-tree system could plausibly drive *bulk* pattern creation from the Pattern Terminal once M6's recipe-viewer integration lands - explicitly future scope, not blocking this milestone.
