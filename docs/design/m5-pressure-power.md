# M5 — Steampunk Power Layer

See [README.md](README.md) for the `PressureConsumer` hook this milestone activates.

## Core mechanic: pressure is a gate first, a speed bonus on top

**Pneumatic machinery, not electric: no pressure reachable means no operation at all - but more pressure than the bare minimum makes it run faster, not just "on".** Steampunk pneumatics can't run dry, the way a redstone-powered machine either has power or doesn't; but unlike a flat on/off gate, building more compressors/tanks/pressure network capacity keeps buying more throughput once a machine *is* running, so investment still pays off into the late game rather than every machine being hard-capped at a fixed rate the moment it's merely "enough". This is why `PressureConsumer.onPressureTick(line)` (defined in [README.md](README.md#cross-cutting-the-pressureconsumer-hook)) returns a continuous multiplier rather than a boolean, but treats its own bottom value as a real gate rather than a floor:

```kotlin
interface PressureConsumer {
    val basePressureCost: Long get() = 0     // pressure/tick required to run at all, at 1.0x speed
    val maxPressureDraw: Long get() = basePressureCost   // caps how much speed extra supply can buy
    fun onPressureTick(line: ArchieEnergyStorage): Double = 1.0
}
```

`onPressureTick` returns `0.0` - a hard gate, never a divisor a caller can safely use - when `line` can't even cover `basePressureCost`; every caller has to check for that and skip its own operation entirely, not merely run it at some reduced rate. Above that floor it scales up toward `maxPressureDraw` the same as before. A machine with `basePressureCost = 0` (the M1–M4 default, for anything not yet given a real requirement) is unaffected by pressure and always runs at 1.0x - this milestone's job is giving real machines nonzero costs and a real network to draw from, not changing any tick-loop structure introduced earlier. See "Hooks: a hard requirement, not a bonus" below for the one consumer kind (`PipeHookType`) that skips its own `PressureConsumer` plumbing entirely and draws/gates directly instead, for the same reason.

## Storage primitive

Reuses `ArchieEnergyStorage : ValueStorage` relabeled as pressure — no new storage primitive needed. The tank and compressor are **encasements** on a `PressurePipeBlock` segment - a promoted `MultipartBlockEntity`, exactly the same block/entity pair an item pipe promotes into (see [m1-pipe-network.md#network-types](m1-pipe-network.md#network-types)), not a standalone pressure-only pair of classes. `CompressorEncasementType`/`PressureTankEncasementType` are ordinary `PipeEncasementType` entries (`compatibleNetworkTypes = setOf(NetworkTypeRegistry.Pressure)`), and their states extend the shared `EncasementHolderState` base - no `Pressure`-prefixed sibling hierarchy:

```kotlin
class PressureTankEncasementState : EncasementHolderState(PressureTankEncasementType.ID) {
    val pressure by energyField(capacity)
}
// registration, on the one shared TileRegistry.Multipart:
TileRegistry.Multipart.exposeEnergyStorage { tile ->
    (tile.encasement.value as? PressureTankEncasementState)?.pressure
        ?: (tile.encasement.value as? CompressorEncasementState)?.pressure
}
```

`CompressorEncasementState`/`CompressorEncasementType` burn a fuel item (furnace-analog, via `AbstractFurnaceBlockEntity.getFuel()`) to fill their own `ArchieEnergyStorage`. Neither the tank nor the compressor is a `PressureConsumer` itself — pressure equalization (below) is what moves pressure around, not a per-tick draw against an active operation the way an extractor or the Crafting CPU is.

Both encasements share one casing shape — an open frame plus per-face arm/cap/none pieces, registered over the same `ConnectingEncasementModelBlock` the Crafting CPU (M4) casing uses (`compressor_part`/`pressure_tank_part`, alongside `crafting_buffer_part`) — but a different cluster-validity rule of their own, `PressureMultiblockManager` (the M4 sibling of `CraftingCpuManager`). A cluster is valid in either of two shapes:

- a **compressor bank**: the lowest Y layer is compressors only, filling its own X/Z rectangle exactly; every layer above is tanks only, each filling that same rectangle (a bare compressor rectangle, no tank layer at all, is valid too);
- an **auxiliary tank**: no compressor anywhere in the cluster — any tank-only cuboid, whatever its width/depth/height.

Both still have to fill their own overall bounding box exactly, same as the Crafting CPU's own cuboid rule. Formation is currently cosmetic only (gates the casing's edge/corner seam fillers, mirroring `CraftingBufferEncasementState.formed`) — no combined-capacity bonus for a valid cluster yet; that's a natural extension if playtesting wants one.

## Pressure piping — its own network, but item pipes conduct it too

`Pressure` is a `NetworkType` (`NetworkTypeRegistry.Pressure`, `managerFor` → `PressurePipeNetworkManager`) that every item pipe carries as a secondary type alongside its own `Item` primary - see [m1-pipe-network.md#network-types](m1-pipe-network.md#network-types) for the general mechanism. `PressurePipeNetworkManager.isMember` is just `Pressure in networkTypesAt(level, pos)`, so a plain item pipe run conducts pressure right alongside items without needing a dedicated brass/rivet run laid next to it - `PressurePipeBlock` (primary `Pressure`, no secondary) only earns its keep where a branch needs pressure with no item transport at all (a compressor bank tucked off to the side, say).

The one place the two still don't merge for free: an item-pipe segment touching a *dedicated* pressure-pipe segment. `PressurePipeNetworkManager.isBoundaryEdge` defers to `PressureNetworkBoundary`, which treats that specific junction (both sides resolve an actual pipe primary type, and they differ) as a boundary unless an `AdapterHookType` hook sits on either face - mirroring `SubnetBoundary`/`InterfaceHookType`'s existing item-network boundary mechanism (M1/M2) exactly. Item-to-item and pressure-to-pressure edges, and an item pipe reaching straight into an `EnergyApi` neighbor, are never boundaries - only the item/dedicated-pressure-pipe join is gated, which happens to be exactly where the adapter's reducer-collar model already sits physically. The mismatch check requires *both* sides to resolve a real primary type, not just an inequality - a non-pipe consumer (the warehouse controller) has no primary type of its own (`null`), and `null` compared against a neighbor's real one isn't a "mismatch" in the sense this boundary means; without that guard, a consumer sitting directly against a dedicated Pressure Pipe (`placeAdjacentPressureSource`'s own shape) would wrongly wall itself off from the very pipe it's touching.

The topology bookkeeping (union-find merge, chunked-BFS split rebuild) is identical in shape to M1's `PipeNetworkManager` — factored into a shared `pipe/network/AbstractPipeNetwork(Manager)` base, with `PipeNetworkManager` (M1, unchanged public API) and `power/network/PressurePipeNetworkManager` as separate concrete implementations underneath it. `PressurePipeNetworkManager` additionally overrides `tick()` to run an equalization pass per network (see below) — the item side has no equivalent, since item transport already moves discretely via `TravelingItem`.

## Pressure line resolution — no network-level bucket

`ArchieEnergyStorage` is a `class`, not `open`, with a private `capacity` — there's no way to synthesize a "network aggregate" instance whose capacity tracks however many tanks are attached. So there is no network-level pressure bucket. Each tank/compressor keeps its own real, NBT-persisted `ArchieEnergyStorage`; "networked" pressure is a per-tick **equalization pass** (`PressurePipeNetworkManager.equalize`, using `TransferUtil.moveValue`) leveling every tank/compressor endpoint on a network toward the same fill *fraction* (not absolute amount, since tank tiers may differ in capacity).

A consumer's own "line" (`PressureLine.find`) is just the *nearest reachable tank or compressor's own storage*, found by BFS over the pressure-pipe graph from the consumer's own position (same shape as `RequestFulfillment.reachablePipes`'s unbounded BFS) — since equalization keeps every endpoint on a network near the same fill level, "nearest endpoint" is a faithful proxy for "the network's pressure," without ever needing a real aggregate. `PressureLine.find` checks the consumer's own position *and* its immediate neighbors for a network membership: since item pipes conduct pressure now, a hook or Crafting CPU leader's own segment is itself often already a network member; a caller that isn't a pipe segment at all (the warehouse controller) still needs the neighbor check - but only across an edge `PressureNetworkBoundary.isBoundaryEdge` itself doesn't flag, the same rule the topology merge already applies; naively unioning in *every* neighbor's network regardless of a boundary between them let pressure "leak" straight across an unbridged junction, confirmed the hard way (a hook sitting directly adjacent to an unbridged dedicated-Pressure-Pipe run could draw from a tank on the far side that its own network topology correctly refused to merge with). Both `PressureLine.find` and `PressurePipeNetworkManager.equalize` also have to probe each network member's *own* position for a `PressureApi` capability, not just its neighbors — unlike an item-pipe endpoint (always a separate, non-member neighbor, like a chest), a tank/compressor encasement is itself both a network member and the endpoint being searched for.

A hook attach/detach can change whether an edge is a boundary (an `InterfaceHookType`/`AdapterHookType` hook appearing or disappearing), but `AbstractPipeNetworkManager.ensureRegistered` is deliberately idempotent - once a position is registered, it never re-examines its own edges again on its own. Left alone, an Adapter placed *after* both sides of a junction were already registered as separate networks (which happens on the very first tick either side exists at all, long before a player gets around to adding the adapter) never actually bridged them - a real, full tank sitting right there stayed permanently unreachable. `MultipartBlock.clickBlockWithItem`/`detachWithWrench` now force both `PipeNetworkManager` and `PressurePipeNetworkManager` to re-evaluate the clicked position's own membership (`onRemoved` + the position's own next-tick `ensureRegistered` re-walking its edges fresh) whenever a hook is attached or detached, the same eviction `removeJustThePipe` already applied to a pipe-type change.

That resync alone wasn't quite enough, though - once hook attach/detach started invalidating network membership on top of ordinary block removal, two *unrelated* invalidations landing in the same pending rebuild batch got far more common, and `AbstractPipeNetworkManager`'s own chunked rebuild (see `m1-pipe-network.md#pipe-network-graph`) used to reprocess its entire pending set with a raw-adjacency-only flood-fill that ignored `isBoundaryEdge` entirely - the clicked position itself always re-registered correctly (same tick, via its own ordinary `ensureRegistered`), but the rebuild running afterward in `SERVER_LEVEL_POST` could still walk straight across an unrelated boundary elsewhere in the same batch and silently reunite two sides that should've stayed split, or stomp an already-correct assignment with a wrong one - hooks/terminals further down the network from wherever the actual change happened, in other words, not the ones right next to it. Fixed at the source: the rebuild now skips anything already registered and respects `isBoundaryEdge` in its own frontier expansion, exactly like `ensureRegistered` always did.

## Throughput gating in practice

- Warehouse gantry (M3): `WarehouseControllerBlockEntity.effectiveGantrySpeed()` multiplies `WarehouseScale.baseSpeedPerTick` by `pressureSpeedMultiplier()` (`onPressureTick`) - a `0.0` multiplier naturally zeroes the speed out (`gantry.tick(0.0)` is a no-op), so the hard gate needs no extra branch here. Every `WarehouseScale` tier, even `COMPACT`, has a nonzero `basePressureCost` - a warehouse gantry genuinely does not move at all with no pressure reachable.
- Crafting CPU (M4): `CraftingBufferEncasementType.advanceJob` computes `state.onPressureTick(...)` once per tick (an active job's own `basePressureCost` is nonzero, an idle leader's is `0` - its own leftover-draining isn't gated, see "Pressure line resolution" above) and, on `0.0`, skips claim/feed/pull entirely for that tick rather than treat the multiplier as a divisor - `advanceSteps` takes the already-computed multiplier as a parameter instead of calling `onPressureTick` a second time, which would double-draw the line.

Only the gantry called through the `PressureConsumer` hook before this milestone (against a throwaway always-empty stand-in) — the Crafting CPU declared conformance but never wired a real line in. This milestone gave both real `basePressureCost`/`maxPressureDraw` values and wired `onPressureTick` to a real `PressureLine.find` result, without touching any of their existing tick-loop structure.

## Hooks: gated the same way, without the speed-scaling layer

Every `PipeHookType` also declares a nonzero `basePressureCost` (differentiated by roughly how much work that hook kind does per tick - `1L` for a purely passive/config-only hook like `FilterHookType`/`SyncHookType`/`ProviderHookType`/`AdapterHookType`, up to `4L` for `PatternProviderHookType`/`CraftingTerminalHookType`'s own heavier conversion/job-tracking work). Hooks don't go through `PressureConsumer`/`onPressureTick` at all, though, unlike the gantry/Crafting CPU above: a segment can carry up to six independent hooks, each needing its *own* gate check, not one aggregate multiplier for the whole segment - `MultipartBlockEntity.tick()` draws each hook's own cost from `PressureLine.find` directly every tick (real, not simulated, extraction) via a small dedicated helper, and skips that hook's own `PipeHookType.tick`/`start` entirely whenever it can't afford it. A hook that's gated on runs at its own flat rate rather than scaling faster with pressure beyond that - `ExtractionHookType` used to scale its own pull interval via `onPressureTick` like the gantry/Crafting CPU do; that's gone now that a hook without pressure simply doesn't tick at all, so it just runs at its flat `EXTRACTION_INTERVAL_TICKS` whenever it's active. `HookHolderState.active` records the gate's own result, driving `BistateHookModelBlock.ACTIVE`'s blockstate (`<hook>_off`/`<hook>_on` model variants, see `BoilerplateBlockStateProvider`) via `PipeHookType.getRenderState` - one shared implementation for every hook kind, since the property means the same thing everywhere. `hooks` is `@Sync`, but a menu-less `BlockEntity`'s `@Sync` fields don't reach clients on their own - `MultipartBlockEntity.tick()` now calls `sendBlockUpdated` once per tick whenever any hook's own `active` actually flipped (not unconditionally, to avoid a packet every tick), the same explicit push `CraftingBufferEncasementType`/`PressureMultiblockManager` already do for `formed`; without it, a hook's own on/off model never visually updated no matter how long `active`'s real value had actually differed, since `hooks.touch()` alone only marks it dirty for NBT persistence, not for pushing to nearby clients.

`CreativePressureSourceBlock`/`CreativePressureSourceBlockEntity` (creative-tab-only, never craftable) backs an `ArchieEnergyStorage` refilled to capacity every tick, for creative-mode building and gametest fixtures that need a reachable pressure source without a real fuel-burning compressor. `PressureLine.find` only ever resolves a network starting from an *adjacent pipe segment*'s own membership (see above) - a non-pipe consumer like the warehouse controller needs a real pipe segment between it and the source, not the source sitting directly next to it.

`PressureNetworkBoundary` (see above) now folds in `SubnetBoundary`'s own item-network split too, not just the item/dedicated-pressure-pipe primary-type mismatch: an `InterfaceHookType` hook facing another hook keeps the two sides' *pressure* separate as well, on the same reasoning - crossing for free there would undermine the logical-network split as much as an item silently routing through would. An `AdapterHookType` hook bridges either kind of boundary.

## Deferred to playtesting / not blocking

- Exact unit/cost balance and the multiplier curve's floor/ceiling — pure playtesting.
- Whether over-pressure should be dangerous (tank rupture/explosion, BuildCraft/IC2-boiler-style) — thematically fun, but real scope/safety-design surface. Optional stretch, not assumed.
- Whether pressure should be networked (current lean, per the vision's framing of pressure as *the* throughput gate) vs. a simpler per-machine local resource — not force-closed here.

## Pipe travel speed

Item pipes move their contents faster the more pressure their own line currently holds — `PipeBlockEntity.refreshPressureState` maps available pressure onto a `1.0`x..`MAX_SPEED_MULTIPLIER` scaling of `SEGMENT_SPEED`, saturating at `PRESSURE_FOR_MAX_SPEED` (2,000, against a compressor's own 4,000 capacity, so one well-fed compressor saturates a run).

Two things make this unlike every other `PressureConsumer` in the mod:

- **It reads without drawing.** The line is probed with a simulate-only `extract(..., true)`, so a pipe run never competes with real machinery for supply. Pipes aren't machines consuming a budget; they move faster through a well-pressurised network the way real pneumatic tube does.
- **It gates at the bottom, but by stopping rather than by skipping a tick.** No line at all, or a line with nothing in it, sets `hasPressure = false` and `speedMultiplier = 0f`: the segment advances nothing, delivers nothing, and — via the `!nextTile.hasPressure` check in the hop branch — is refused as the next hop by the segment before it, which stalls its delivery exactly as a full destination does. A dead run therefore backs up at the seam and holds what it already carries, rather than quietly swallowing everything pushed into it. That is the intended rule: a pneumatic tube with no air behind it is a pipe full of stationary cargo, and without it a pipe network is free infinite transport that pressure merely accelerates.

Nothing has to *initiate* against a dead segment either — every `PipeHookType` is already gated on its own `basePressureCost` (see "Hooks" above), so an extractor on a dead run never ticks in the first place. The hop check covers the other direction: a live run feeding into a dead one.

`PressureLine.find` walks its network's members looking for an endpoint, which is far too expensive per pipe per tick, so the reading is cached and refreshed every `PRESSURE_REFRESH_INTERVAL_TICKS` — **while the segment is alive**. A dead segment re-reads every tick instead, since that throttle would otherwise be how long a run stays stopped after its supply returns, and how long a freshly placed or freshly loaded segment refuses to carry anything while its own network is still being registered. `PressureLine.find` memoises per network per tick, so every dead segment on one network shares a single walk.

The multiplier is synced to clients on `PipeContentsSyncPacket` so `PipeContentsClientCache`'s dead reckoning runs at the same rate the server does. It also makes every pipe-travel *estimate* (`RequestFulfillment`'s `onDispatch` ticks, `WarehouseControllerBlockEntity.estimateRetrieveTicks`' pipe leg) a worst case rather than a fixed figure, since those all assume the baseline. That direction is the safe one: a reserved-slot placeholder whose item arrives before its progress bar fills just clears early, where the reverse would leave a full bar sitting there.
