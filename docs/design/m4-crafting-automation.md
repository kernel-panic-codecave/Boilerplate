# M4 — Crafting Automation

See [README.md](README.md) for shared conventions and [m3-warehouse-storage.md](m3-warehouse-storage.md) for `WarehouseIndex`/the gantry job queue this builds on.

## Pattern representation

Built on vanilla recipes rather than inventing a new format: a `Pattern` is a snapshot taken at encode time (AE2-style pattern encoding, not a live `RecipeHolder<CraftingRecipe>` reference - a later game/recipe change should never retroactively invalidate an already-encoded pattern), or a manual input/output list for non-vanilla "processing" conversions:

```kotlin
data class Pattern(
    val inputs: List<SItemResource>,               // up to 9, one per grid cell for CRAFTING (positional), an unordered bag for PROCESSING
    val outputs: List<SResourceStack<SItemResource>>, // 1 for CRAFTING, up to 9 for PROCESSING
    val kind: PatternKind,                          // CRAFTING | PROCESSING
)
```

No separate per-input quantity field - a resource's own required count is just how many of the 9 `inputs` entries hold it (`Pattern.requiredInputs()`), the same "count via slot occupancy" shape a real crafting grid already has.

**Patterns are items, not block-owned state** - a `PatternItem` (one item type; blank or encoded is just its own stack-component data, the same way an empty vs. written book share one item type). `PatternItemData(stack)` gives it the same `field`/`itemField` delegate API a `BlockEntity` gets (`NBTHolder.item(stack)`, backed by the vanilla `CustomData` component); its one field, `pattern: Pattern?`, is backed by a private 0-or-1-element `List<Pattern>`, not a genuinely nullable field - knbt's `AbstractNbtEncoder` doesn't support `encodeNull` any more than it supports `encodeEnum` (the same latent gap `PatternKindSerializer` already works around below), so a real nullable serializer crashes the instant a stack goes back to blank. A pattern travels through pipes/inventories/warehouses like anything else, rather than living pinned to whichever block it was authored on.

`PatternEncoder.encode(level, kind, grid, patternOutputs)` snapshots a plain `ArchieItemStorage` grid/pattern-outputs pair into a `Pattern` of the *explicitly requested* `kind` - not auto-detected by whether the grid happens to match a real recipe. `PatternKind.CRAFTING` matches `grid` against `RecipeManager`/`CraftingRecipe.assemble` and snapshots the *actual assembled* result (`null` if nothing matches; `patternOutputs` unused); `PatternKind.PROCESSING` snapshots every non-empty slot of `patternOutputs` as-is, up to all 9, regardless of whether `grid` also happens to match a vanilla recipe (`null` if none are set). A no-op either way if `grid` itself is entirely empty. Kept as a standalone object, not inlined into any menu, so it's directly testable without a real menu/player - see `PatternEncoderGameTest`.

Caught the same latent knbt bug `FilterMode`/`RoutingModule` did (see `docs/design/m2-sorting-routing.md`): a plain enum's default `encodeEnum` isn't supported by knbt's encoder at all. `PatternKindSerializer` (encode/decode by name) fixes it the same way `FilterModeSerializer` does - confirmed by an actual crash on `PROCESSING` before the fix.

## Pattern Provider hook

A `PatternProviderHookType` hook (`providesItems = true`) holds up to 9 `PatternItem` stacks in its own slots and decides *what* to run against whatever's on its own attached face - "any adjacent inventory," the same way `ProviderHookType`/`ExtractionHookType` reach into any generic `ItemApi.BLOCK`-exposed inventory.

A real, placed vanilla crafting table is the special case for a `CRAFTING`-kind pattern, detected by block state (`Blocks.CRAFTING_TABLE`) rather than block entity - a crafting table has none of its own. `tickVanillaCraftingTable` resolves **instantly**: a pattern's own `Pattern.outputs` were already assembled once, at encode time, so running it is just the same generic extract-inputs/insert-outputs conversion every pattern kind uses - no live recipe lookup needed. A `while` loop, not one run per tick, since "instant" means a whole buffered batch converts in one go. Both ingredient staging and the assembled result live entirely as virtual hook state, since the table itself has no inventory to hold either:

- **`PatternProviderHookState.patternBuffers`** - one `ArchieItemStorage` per pattern slot, lazily created via `bufferFor(index)`, isolated from every other slot's own staged ingredients so two patterns sharing an input (planks, say) never collide.
- **`PatternProviderHookState.patternOutputBuffers`** - the symmetric output side, via `outputBufferFor(index)`, exposed externally as pullable network stock through `PatternOutputIO` (`ProviderSource.storage`'s special case for this exact combination - a crafting table's block position exposes no capability at all).

Any other target (a vanilla furnace, say, or a future crusher - a `PROCESSING`-kind pattern's own real, self-driving machine) falls back to a single-slot behavior (`tickGenericTarget`): `activeSlot` tracks the one pattern presumed in flight, detected by plain ingredient presence in the target's own combined `get()`/`size()` view rather than a directed `extract(simulate=true)` (which only reads a directed storage's *output* side - a real bug hit and fixed here: a target with separate `grid`/`output` slots always reads a simulated extract of *input* ingredients as unavailable). Either way, the hook's own held patterns' outputs are exposed as pullable network stock through the *existing* provider-style pull machinery (`providesItems = true` is all that's needed - see `RequestFulfillment.ProviderSource`).

`PatternBufferIO` bridges a hook's own `patternBuffers` into one `CommonStorage`, exposed directly on the hook's own block position - what a delivery aimed at this hook (rather than its target) actually inserts into. Its `insert` distributes a delivered resource round-robin across every pattern slot that still wants it (topping each demanding slot up to only its own *next* single-run boundary per pass, cycling through every slot before starting a second pass) rather than filling earlier slots to their own full multi-run cap first - a single `insert` call has no way to know whether a separate call, for a *different* slot, is about to want the same resource on a later tick, and greedily filling one slot first would starve the other indefinitely.

A table doesn't know its own recipes any more than a furnace does - the pattern list lives entirely on the hook, never on the target block. `RequestFulfillment.reachablePatternProviders(level, from)` returns `PatternProviderSource(hookPos, direction, state)` for every reachable `PatternProviderHookType` hook - the crafting resolver's, the terminal's, and a Crafting CPU's own entry point for "what can produce X."

## Encasements

The whole-segment counterpart to the per-face hook system (`docs/design/m1-pipe-network.md`): a `PipeEncasementType` wraps an entire pipe segment rather than attaching to one of its faces, and lives in its own synced `pipe_encasement_type` registry (`Registrars.ENCASEMENT_TYPE`/`EncasementTypeRegistry`) so a new encasement kind is a registry entry with its own `EncasementHolderState` subclass, not a new standalone block. Its API is `PipeHookType`'s minus every `Direction`: `createState`/`tick`/`hasMenu`/`createMenu`, plus `onAttached`/`onRemoved` for a type that maintains topology of its own, and a `coreShape`.

State rides on the existing `HookBlock`/`HookBlockEntity` pair rather than a third pipe variant - `HookBlockEntity.encasement`, over a single-key `nestedMapField` (`encasements`, keyed `ENCASEMENT_KEY`). A map for one entry because Archie's scalar `nestedField` factory takes no tag to inspect, so it can neither pick which concrete subclass to rebuild - the same type discrimination `hooks` needs - nor represent "no encasement"; a `nullableNestedField(factory: (CompoundTag) -> T)` upstream would be the tidy fix. A plain pipe promotes to `HookBlock` on either a hook or an encasement, and `HookBlock.demoteIfBare` demotes it back only once **both** are gone.

**Hooks and an encasement coexist on one segment**, which is what fixes the shape of `coreShape`: the default is a 10x10x10 housing (pixels 3-13) standing in for the pipe body's own 6x6x6 `CORE_SHAPE`, chosen so a hook's own 6px-deep shape and a connected arm's own 5px reach both still stand proud of the casing. No per-face cutouts, no dynamic shape subtraction - hooks stay visible, clickable, pick-blockable and breakable. The one adjustment is in `PipeBlock.shapeForDirection`: on an encased segment a face with no hook resolves to *nothing* rather than to its arm, since the casing covers that arm - otherwise clicking the middle of a bare casing face would dead-end on an arm instead of falling through to the core, where the encasement's own menu lives. `HookBlockEntity.pendingMenuFace` is nullable for the same reason: `null` means "the encasement", not a face.

Rendering follows the hook path exactly - `HookBlockEntityVisual` draws a third Flywheel instance for the casing, keyed on the encasement type id, looking up `<type path>_encasement#inventory` (guaranteed baked by that type's own `EncasementItem` icon, just as `<type path>_hook` is by a `HookItem`).

## Crafting CPU (multiblock)

[Decision #4](README.md#resolved-architectural-decisions) (superseding an earlier draft that had a dedicated Assembly Table machine): ingredients for a whole plan are pre-calculated and claimed up front, staged in shared storage, and shuttled out to whatever target each step needs rather than a machine driving its own crafts directly. The **Crafting Buffer** is an *encasement* (`CraftingBufferEncasementType`), not a block of its own: adjacent encased segments auto-cluster into one shared-capacity "CPU" that runs **one job at a time** - bigger cluster means more storage room, not more parallel jobs; genuine parallelism comes from placing a second, physically separate cluster.

Being an encasement is what makes the CPU an ordinary participant in the network instead of a special case bolted onto its edge. It *is* a pipe segment, so every routing call starts from its own position and every shipment it sends leaves through its own `travelingItems` - no "find me some adjacent pipe to search from" indirection, no six-way neighbour scan to inject an item, and no exclusion rule in `PipeRouter.step`: an encased segment satisfies `isPipe`, so the push BFS walks *through* it as transit and never evaluates it as a candidate destination at all, leaving its storage reachable only by the `findRouteTo`-targeted claim/feed logic of the job that owns it. Items also route straight through a CPU sitting inline in a run, rather than a cluster having to hang off it as a leaf branch. One consequence worth knowing: `PipeRouter.isPipe` treats a segment whose `pipeBlockId` is still `NONE` as not a pipe, so an encasement placed against air is inert until a pipe is placed into it - exactly as a hook placed the same way is.

**Clustering** (`CraftingCpuManager`, one instance per `ServerLevel`, mirroring `PipeNetworkManager`'s own cached-topology idiom): a `Cluster` is every axis-adjacent encased segment reachable from a given position (BFS, capped at `MAX_CLUSTER_SIZE = 64`), cached until `invalidate`d - driven by the encasement type's own `onAttached`/`onRemoved`, which invalidate both that position and all six neighbours. Its `leader` is deterministically the lowest `BlockPos.asLong()` among its members - every member computes the same answer without a persisted "controller" flag. A cluster is only **valid** when its members fill their own bounding box exactly - 1x1x1, 2x2x1, 2x2x2... a complete cuboid, AE2's formation rule; an L-shaped or otherwise incomplete arrangement is inert as a CPU: no member ticks jobs, `reachableCraftingCpus` skips it so terminals can't submit to it, and each segment's storage stands alone via `combinedStorage`'s own fallback until the shape is completed. A component too big for the cap is invalid outright rather than silently truncated into half-functioning.

**`CraftingCpuStorage`** concatenates every cluster member's own `localStorage` (9 slots each) into one `CommonStorage<ItemResource>` - this *is* "expanding as it needs more space": encasing another adjacent segment grows the shared pool, no dynamic per-slot NBT trick needed. `CraftingBufferEncasementState.combinedStorage(tile)` resolves this fresh (via the cluster's current member list) rather than caching it, so a cluster that just grew or shrank is always seen correctly - falling back to just that member's own slots whenever the arrangement isn't a valid cuboid. It's exposed on each member's own block position through `TileRegistry.Hook`'s `exposeCommonItemStorage`, ranked between the face-matched hook lookups and the face-less fallbacks: an encasement has no face to mismatch on, so it's the one unambiguous answer for a direction-less query, and a job's own pull-back (always targeted at the cluster's own position) must not be diverted into a pattern buffer that merely happens to share the segment.

One `activeJob` per cluster plus a `backlog: ArrayDeque<CraftingBufferJob>` (unbounded today, not a flat cap) lets a terminal queue onto a busy cluster instead of being flatly rejected - `enqueue(plan)` lands straight on `activeJob` if idle, onto the backlog otherwise, returning a job id a submitting terminal polls via `jobStatus(id)`. `backlogDepth()` (active job plus queue length) is what a terminal compares across several reachable clusters to pick the least-busy one (`RequestFulfillment.reachableCraftingCpus`, one entry per distinct cluster leader, deduped the same way `reachableWarehouses` is - and scanning the reachable pipes themselves, since a cluster's members *are* pipes).

### Reservation

Ephemeral (not persisted) claim ledger on `WarehouseControllerBlockEntity`, alongside its existing transient `jobs`/`pickupQueue`:

```kotlin
private val claimed: MutableMap<ItemResource, Long> = mutableMapOf()
fun claimAndEnqueue(resource: ItemResource, amount: Long, deliverTo: DeliveryTarget): Long
```

`WarehouseIndex.locations` itself only decrements once a real extraction happens (in `pickUp`, which can run many ticks after a retrieval is queued) - without `claimed`, two concurrent claims against the same live numbers could double-count the same physical items. `claimAndEnqueue` walks `index.locations[resource]` in order, skipping past whatever `claimed` already accounts for, enqueuing one `GantryJob.Retrieve(..., claimed = true)` per rack slot it draws from, and bumping `claimed[resource]` by however much it actually claimed (which can be less than requested, or zero). `pickUp`'s own `Retrieve` branch releases the reservation (`releaseClaim`) the instant that specific job is attempted, regardless of whether the real extract came up short - an ordinary, unclaimed `enqueueRetrieve` job never touches `claimed` at all.

**Timing**: claiming happens every tick a job has anything still outstanding in `CraftingBufferJob.outstandingStockClaims` (seeded from `CraftingResolver.Plan.stockPulls` on promotion), not just once - a job's own raw-material needs keep retrying against a reachable warehouse until fully claimed, the same throttle-free retry shape the rest of a job's own step feeding uses. Only `stockPulls` (raw materials) are ever claimed this way - an intermediate resource a step of the same job will produce itself is never claimed from a warehouse.

**Shortfall handling**: optimistic, not blocking. A step's own inputs start feeding the moment they're available, even while a different resource's claim is still outstanding elsewhere. Genuine insufficient stock just stalls, retried every tick.

## Resolution

`CraftingResolver.resolve(target, amount, stockOf, patternFor)` resolves into a **DAG**, not a tree — memoized per-resource within one resolution pass so, e.g., two branches both needing iron ingots share one sub-request rather than double-counting. `stockOf`/`patternFor` are plain functions, not tied to `WarehouseIndex`/`PatternProviderHookState` directly, so the algorithm itself is a pure, directly-testable unit; `CraftingRequest.resolve(level, from, target, amount)` is the real wiring, summing stock across every `WarehouseControllerBlockEntity` reachable from `from` plus every `providesItems` hook reachable the same way (`reachableProviders(...)` - exactly the sources an ordinary withdrawal pulls from, so raw materials sitting behind a provider/sync hook count toward a plan like shelf stock; only warehouse-side stock is claim-tracked, so a Crafting CPU's own claimed stock stays excluded there) and taking the first pattern match found across every reachable `PatternProviderHookState`'s own held patterns (`reachablePatternProviders(...).flatMap { it.state.heldPatterns() }`).

Turned out to need two passes, not one interleaved recursion - a shared resource's *total* demand (needed to decide how much actually has to come from stock vs. crafting) isn't known until every consumer of it has been discovered:

1. **Discover** - DFS from `target`, recording each resource touched in post-order (a resource's own pattern inputs are recorded before the resource itself); a resource reached while still in-progress further up the same branch fails fast as `Result.Cyclic`, rejecting an impossible/self-referential pattern chain cleanly instead of recursing forever.
2. **Demand** - walk that post-order **in reverse** (target first, deepest leaf ingredients last) accumulating each resource's total demand as its consumers are visited; by the time a resource itself is reached, every consumer that could ever add to its demand already has, since a consumer always sits earlier in the reversed order than what it consumes. A resource still short after stock is checked against its own pattern - `Result.Unresolvable` if it has neither.

The result (`CraftingResolver.Plan`) lists `steps` (one `CraftStep(pattern, runs, resource)` per pattern actually needed, in bottom-up order - a leaf ingredient's own craft always precedes whatever consumes its output; `resource` is the demand that sized `runs`) and `stockPulls` (total pulled directly from stock, per resource, across the whole plan). `CraftingResolver.maxCraftable(target, upperBound, stockOf, patternFor)` binary-searches over `resolve` itself for the largest amount still resolvable - see "Terminal" below.

## Terminal family

Three sibling hook types share one submitted-job list and one Store-tab shape, each a near-duplicate menu/screen class rather than a real class hierarchy - `ComposeBlockContainerMenu`'s own self-referencing `SELF` type parameter makes real inheritance awkward, and every other hook type in this mod already accepts that tradeoff:

- **`TerminalHookType`** - the plain terminal: search/withdraw stock, browse/request autocrafts, view the job tree.
- **`CraftingTerminalHookType`** - everything the plain terminal does, plus a real 3x3 grid for instant, manual, real-item crafting.
- **`PatternTerminalHookType`** - everything the plain terminal does, plus a *ghost* grid for authoring patterns without needing the real items in hand.

All three inherit `TerminalHookState.submittedJobs`/`.output` wholesale (`TerminalHookState` is `open`); `advanceTerminalJobs` (the polling driver, see "Execution" below) is a plain top-level function in `TerminalHookType.kt`, not an object method, specifically so the other two can drive the exact same queue without needing real inheritance from a Kotlin `object`.

### Store tab

One tab, not a separate "Store" and "Craft" pair - `StoreResultsGrid` (`pipe/gui/StoreResultsGrid.kt`, shared across all three menu classes since it takes plain data/callbacks rather than a concrete menu type) merges current stock (`TerminalHookMenu.results`) and the craftable catalog (`TerminalHookMenu.craftableResources` - the distinct resources any reachable `PatternProviderHookState`'s own held patterns can produce) into one grid, filtered by a sidebar cycle button (`StoreViewMode`: Stock / Craft / All - the AE2-terminal-style toggle, cycling on click) instead of a dedicated autocraft-browsing tab:

- An entry with real stock (`amount > 0`) shows its real count; a plain click opens `requestQuantityDialog` and withdraws - unchanged from before.
- An entry with **no** stock but a matching pattern (`craftable = true`, `amount == 0`) shows `"Craft"` as its count text instead of a number, and a plain click opens `requestCraftQuantityDialog` directly - there's nothing to withdraw.
- An entry that's **both** in stock and craftable keeps the normal withdraw click; a **middle-click** additionally opens the autocraft dialog for it (`TerminalSlot`'s own `clickHandler`/`onMiddleClick`, the same mechanism `GhostSlot` already used for filter-card editing - detecting an actual middle click can't happen inside `Clickable` itself, since a `PointerEvent` doesn't carry which button triggered it, only `DragEvent` does; it's intercepted one level up, at the screen's own `mouseClicked` override).

A real, `Slots`-backed row of nine `"output"` slots sits underneath the grid either way - a manual withdrawal delivers straight into the terminal's own `TerminalHookState.output`, not an external chest wired to some other face. A **finished crafting job never lands here** - its result (and any byproduct) is pushed back into ordinary warehouse storage by whichever Crafting CPU cluster ran it, exactly like an ordinary withdrawal never happened (see "Execution" below). `PipeBlockEntity.tick()`'s own hop-vs-deliver decision needed a small general fix for a manual withdrawal to actually work: `val isFinalHop = item.path.size == 1` is now an additional bypass alongside the existing `SubnetBoundary`-specific one, since a route's own last waypoint should always deliver regardless of whether it happens to be pipe-shaped (a terminal's own position is) - previously only interface hooks had this carve-out, and a terminal's own delivery silently jammed without it.

- **Preview** - `requestCraftQuantityDialog`'s own quantity field re-sends `RequestCraftPreviewPacket(resource, amount)` on every change (a `LaunchedEffect`), and the server replies with `CraftPreviewPacket(resource, maxCraftable)` via `CraftingResolver.maxCraftable`. The dialog's "Craft" button stays disabled until `maxCraftable > 0`.
- **Request** - a bespoke client→server `CraftingRequestPacket(resource, amount)` - an *action*, not state, one of the few places this milestone needed a packet rather than reusing a search/preview round-trip shape.
- **Job status** - a plain `String` (`HookBlockEntity.craftJobStatus`), `@Sync`'d the ordinary NBT block-entity way - superseded for anything detailed by the Tree tab (below), but still the quick-glance summary.

### Crafting Terminal: instant, real-item crafting

No physical "Craft" button - the grid sits right under the Store tab's own output slots, and its result slot (`LiveResultSlot`, a `FakeSlot`, never a real vanilla `Slot`) mirrors a real vanilla crafting table exactly: a live, server-computed preview (`InstantCrafting.match`, polled via `RequestCraftGridPreviewPacket`/`CraftGridPreviewPacket` rather than derived client-side, matching every other dynamic value this menu surfaces), a plain click crafts once onto the cursor (refused - grid untouched - if the cursor already holds something incompatible, or would overflow its own max stack), and a shift-click quick-crafts repeatedly straight into the player's own inventory until the grid stops matching, the inventory has no room, or a `MAX_QUICK_CRAFT` (64) safety cap is hit. `InstantCrafting` (`crafting/InstantCrafting.kt`) is the standalone, directly-testable object behind both the preview and the actual craft - `CraftingTerminalHookMenu.craftOnce`/`sendGridPreview` are thin wiring over it, not where the logic lives. Entirely independent of the Crafting CPU - this is a real, player-supplied grid resolved on the spot, not a network request.

### Pattern Terminal: authoring patterns without real items

Same grid position, but every cell is a *ghost* (`GhostSlot`/`GhostSlotGrid`, the same reference-only widget `SortingHookState.filter` already uses - left-click with an item held *copies* its identity in without consuming it, left-click an occupied cell empty-handed clears it). An explicit `RadioGroup` toggles `PatternTerminalHookState.patternKind` between the two `PatternKind`s, rather than `PatternEncoder` auto-detecting one from the grid:

- **Crafting** - the ghost input grid's positions matter, matched against a real recipe at encode time; a hint line, not a live preview, explains this (a live ghost-driven preview was judged not worth the added complexity here, unlike the Crafting Terminal's real-item one).
- **Processing** - the ghost inputs are an unordered bag (same as before), but the output side becomes its own 3x3 *ghost output* grid (`ghostOutputs`/`ghostOutputAmounts`, up to 9 distinct manually-specified outputs, each with its own amount) instead of one forced-single slot - `GhostSlot`/`GhostSlotGrid` grew an optional `amount`/`onAmountScroll` pair for this (display via `FakeSlot`'s existing count-badge parameter; adjusted by scrolling over an occupied cell, `+1`/`-1` per notch, clamped `1..64`).

A real, persistent `blankPatterns` slot (`Slots("blankPatterns", 1, 1)`) holds the stack of blank `PatternItem`s encoding draws from - not the player's own inventory, so the terminal itself can be pre-stocked and left alone. `PatternEncoder.encodeAndConsume(level, kind, grid, patternOutputs, blankPatterns, deliverTo)` is transactional: the blank is only actually consumed once a *simulated* insert into `deliverTo` (the terminal's own `output` slots) confirms there's room, so a full output row never silently eats a blank pattern for nothing. It consumes the blank via `ArchieItemSlot.remove` on the specific slot index, not `ArchieItemStorage.extract` by resource - see "Known gaps" below for why.

## Node-based crafting job tree (Tree tab)

A third tab, present on all three terminal types, replacing a plain status line with a real, pannable node graph of an in-flight job - "kind of like the advancements menu," per its own design ask. `CraftingBufferJob.toTree()` builds a `CraftJobTreeNode` (a plain, network-serializable recursive DTO: `resource`/`amount`/`status`/`done`/`progress`/`children`) rooted at the step producing the job's own `target`, recursing into whichever of its own required inputs also has a step producing them - `CraftingBufferJob.stepStatus(index)` derives each node's status text purely from the job's existing bookkeeping (`tableForStep`/`fedAmounts`/`done`), no new persisted state needed. A resource needed by more than one consumer appears once *per consumer* rather than being deduplicated into a shared node - a plain tree, not a compacted DAG, given how small a job's own tree realistically gets; not worth a real graph-layout algorithm.

Laid out target-last (`RootAlignment.END`): the target sits rightmost with the steps it depends on extending leftward, so the view reads left-to-right in production order - raw material first, finished item last.

A shared resource's column has to account for *every* consumer of it, not just whichever one reached it first. `NodeTreeView` lays each node one column past its deepest parent, so `CraftingTreeView` precomputes each resource's full consumer set and, wherever a resource is declared, adds an edge from every other consumer via `NodeBuilder.dependsOn` **on the shared node itself, naming the consumer**. That direction is the subtle part: `dependsOn` registers the named node as a *prerequisite* (a parent), so calling it the other way round - on the consumer, naming the ingredient - declares the ingredient as the consumer's parent, the exact inverse of what this tree means. That inversion is what put `logs -> planks -> sticks`, `sticks + planks -> pickaxe` on screen as *sticks, planks, pickaxe*: planks was declared under the pickaxe first, then sticks' own repeat of it registered planks as sticks' prerequisite, laying sticks out one column past the planks it's cut from.

`RequestCraftJobTreePacket`/`CraftJobTreePacket` carry the tree to the client on request (the Tree tab polls it, same `LaunchedEffect` cadence as job-status polling), dispatched through a `CraftTreeMenu` interface all three terminal menus implement - the same reason `CraftPreviewMenu` exists for the craft-preview slice of this same dispatch problem. Server-side, `sendCraftTree` reads each of the menu's own `TerminalHookState.submittedJobs` straight off whichever Crafting CPU cluster is actually running it (`craftingBufferAt(level, ref.cpuLeaderPos)?.jobStatus(ref.jobId)?.toTree()`) - a still-queued job (not yet promoted off that cluster's own backlog) simply contributes no tree, same as `toTree()`'s own `null` for a steps-empty job.

`PannableCanvas` (`pipe/gui/PannableCanvas.kt`) is a generic click-drag-panned, scissor-clipped viewport, built on the same `Layout`/`Renderer` primitives `Scrollable` uses (minus the scrollbar and lerp animation - a node graph pans 1:1 with the drag). `CraftingTreeView` lays a `CraftJobTreeNode` out over it column-per-depth (pre-order row assignment, not a compacted layout), connected by simple two-segment elbow connectors drawn directly via `GuiGraphics.fill`.

## Execution

Resolving a request (`CraftingRequest.resolve`) only produces a `CraftingResolver.Plan` - actually running it belongs entirely to a Crafting CPU cluster, never the submitting terminal. `AbstractTerminalHookMenu.submitCraft` resolves the plan, hands it to the least-busy reachable cluster (`RequestFulfillment.reachableCraftingCpus(...).mapNotNull { ... }.minByOrNull { (_, buffer) -> buffer.backlogDepth() }`), and records a `SubmittedJobRef(cpuLeaderPos, jobId)` on the submitting face's own `TerminalHookState.submittedJobs` - or reports `"No reachable Crafting CPU"` via `HookBlockEntity.craftJobStatus` if none is reachable at all. `advanceTerminalJobs` then just mirrors whatever the CPU reports: it reads `submittedJobs.firstOrNull()`, copies that job's own `status` into `craftJobStatus`, and drops the ref once the job is done (or the CPU/job itself is gone - a reload only costs *that terminal's own visibility* into the job, not the job itself, a real improvement over a terminal owning execution directly).

On the cluster's own leader, `CraftingBufferEncasementType.tick` → `advanceJob` drives whichever job is active:

- **Claiming** - every tick a job has anything left in `outstandingStockClaims`, the leader pulls from reachable provider hooks first (`RequestFulfillment.fulfillFromProvider`, looped - it serves one source per call; an immediate, unreserved extract-and-route, so there's nothing to double-commit), then tries `WarehouseControllerBlockEntity.claimAndEnqueue` against every reachable warehouse until fully claimed (see "Reservation" above).
- **A steps-empty plan** (already fully covered by stock) just waits for its claimed stock to actually arrive in the cluster's own `combinedStorage` (`advanceStockOnly`) - there's no bypass straight to the terminal; even a trivial request round-trips through the CPU and back out to storage, keeping "results always land in storage" uniform.
- **A multi-step plan** (`advanceSteps`) resolves each `CraftStep` to a reachable `PatternProviderHookState` holding a matching `Pattern` (`tableForStep`/`hookPosForStep`/`hookFaceForStep`/`patternIndexForStep`, resolved once and cached for the rest of that step), then every tick pushes each step's still-unfed inputs out of the cluster's own storage toward that target (`pushToNetwork`, a real pipe delivery leaving the cluster's own segment) - to the resolved hook's own `PatternBufferIO` position for a `CRAFTING`-kind step (the vanilla table itself has no inventory to deliver into), the target's real position otherwise. Every `PULL_INTERVAL_TICKS` (40, matching the old per-job model's cadence), it retries pulling each step's own produced output back into the cluster (`RequestFulfillment.request`) - throttled, not every tick, since a target's own processing (a furnace's burn time, a vanilla table's instant conversion) takes real time to produce anything to pull.
- **Completion** is gated on a *live* read of the cluster's own storage (`amountIn(combinedStorage(tile), job.target) >= job.targetAmount`), not on how much has merely been *dispatched* - `RequestFulfillment.request`'s own contract counts an in-flight `TravelingItem` as already dispatched, so gating on that instead would flip a job to `done` (and start draining) before a still-travelling delivery ever actually arrived.
- **Draining** (`drainEverything`) only starts once `done` - the target itself, plus any byproduct - one resource extracted and pushed to any reachable accepting destination per tick, via a real pipe delivery leaving the cluster's own segment. Only once every resource is drained does `activeJob` clear and the next backlog entry get promoted. Step-advancement and draining are deliberately mutually exclusive within one tick (`if (!job.done) { ... }`) - running both together would have the return-leg pull fight the drain over the exact same resource, since an emptied machine inventory is just as valid an "accepting destination" as the warehouse the drain was aiming for.

Covered end-to-end by `CraftingBufferGameTest` (single-step craft draining into a reachable rack, not the submitter, plus the same craft with no warehouse at all - raw materials claimed straight out of a provider hook's chest), `CraftingBufferMultiStepGameTest` (a chained intermediate flowing through the CPU to a second machine), `CraftingBufferVanillaTableGameTest` (the `CRAFTING`-kind instant path), `CraftingBufferBacklogGameTest` (a second job queuing rather than running alongside the first), `TerminalCraftingCpuIntegrationGameTest` (terminal submits, polls, and drops its ref once the CPU finishes - result never lands in the terminal), `CraftingCpuManagerGameTest` (cluster/leader detection), `WarehouseReservationGameTest` (the claim ledger), `PatternProviderHookGameTest` (the hook's own reactive behavior against a real crafting table/generic target), and `CraftingBufferJobGameTest` (`toTree`/`stepStatus` in isolation, against a hand-built job).

## Delivery routing

A `HookBlockEntity` can carry up to six independent hooks, one per face - a delivery aimed at a *specific* one (a Crafting CPU job step's own pattern-provider hook, a terminal withdrawing to itself) can't rely on `PipeBlockEntity.tick()`'s own arrival-direction computation to identify which face it means: that direction reflects whichever neighboring pipe segment the item happens to arrive from - pipe network topology - not which face the caller actually intended, and the two routinely differ (a hook mounted on the EAST face reaching into a target, fed by a pipe network that happens to approach from the SOUTH). `TravelingItem.targetFace`/`DeliveryTarget.Pipe.face` thread the caller's own known face through delivery instead, overriding the topology-derived direction at the final hop; `RequestFulfillment.request` gained a matching `deliverFace` parameter, and `CraftingBufferJob.hookFaceForStep` records each step's own resolved face alongside `hookPosForStep`. `TileRegistry.Hook`'s own storage exposure checks that specific face first for every hook type that can legitimately repeat across faces of one block (`InterfaceHookState`, `PatternBufferIO`, `TerminalHookState.output`), falling back to a first-match-on-any-face search only when no face was given - preserving old behavior for the (still common) case of a caller with no specific face in mind.

A Crafting CPU cluster needs no such indirection of its own: each member *is* a pipe segment, so its own position is a valid search origin for `RequestFulfillment`'s reachability BFS and a valid delivery destination, and it injects shipments through its own `travelingItems` rather than a neighbor's. `WarehouseControllerBlockEntity` still scans its six neighbors to reach the network, since it genuinely isn't pipe-shaped.

## Known gaps

- **`ArchieItemSlot.extract` unreliable for component-bearing items** - intermittently fails to match a stack carrying real `DataComponent` data (confirmed with a blank `PatternItem`'s own `CustomData` component) via `extract`'s own `resource.test(unit.toStack())` comparison, even when the exact same slot's `getItem()` reads back correctly moments earlier. Worked around in `PatternEncoder.encodeAndConsume` by consuming via `ArchieItemSlot.remove` on the known slot index instead (no resource-equality check involved at all); not fully root-caused. See `[[archie-itemslot-extract-by-resource-unreliable-for-component-items]]` memory.
- **A previously-crashing Archie bug, now fixed upstream**: `KOps$Nbt`'s own list-building helper (`net.kernelpanicsoft.archie.serialization.KOps`) force-unwrapped a `null` conversion result for a genuinely empty NBT list (`ListTag.fromMinecraft` intentionally returns `null` for an untyped/empty list - there's no vanilla tag-type byte to recover a type from), crashing `HookBlockEntity.tick()` on every tick a real item slot held a blank `PatternItem` (whose own `patternList` field is an empty list when blank). Fixed in Archie directly (special-cased the empty case), republished to `mavenLocal()`; `PatternTerminalHookGameTest.testBlankPatternInARealSlotSurvivesRepeatedTicking` is the regression test.
- **Terminal-family packets cast too narrow** - every packet shared across all three terminal menus (`RequestTerminalSearchResultsPacket`, `RequestCraftPreviewPacket`, `CraftPreviewPacket`, `CraftingRequestPacket`, `TerminalItemDepositRequestPacket`, `TerminalItemWithdrawRequestPacket`, `TerminalSearchResultsPacket`, `RequestWarehouseDefragPacket`, `CraftableListPacket`, `RequestCraftableListPacket`) casts `containerMenu` to the concrete `AbstractTerminalHookMenu` only, not a shared interface - a player with a `CraftingTerminalHookMenu`/`PatternTerminalHookMenu` open fails every one of those casts and the handler silently no-ops. `CraftJobTreePacket`/`RequestCraftJobTreePacket`/`CraftGridPreviewPacket`/`RequestCraftGridPreviewPacket` got this right from the start via dedicated interfaces (`CraftTreeMenu`, concrete-type for the grid preview since it's Crafting-Terminal-only) - the older, pre-existing packets still need the same treatment. See `[[terminal-family-packets-cast-too-narrow]]` memory.
- A `CraftingBufferJob`'s per-step pattern-provider target is picked once, greedily, and never reassigned - a target going offline (broken, or its patterns edited) mid-job stalls that job rather than re-resolving onto a different one.
- `RequesterHookType` has no in-flight-request tracking - a delivery slower than its own `REQUEST_INTERVAL_TICKS` can get double-requested. Predates this milestone; see `[[requester-hook-no-inflight-tracking]]` memory.
- Ingredient remainders (an emptied bucket, say) from `CraftingTerminalHookMenu`'s instant crafting aren't handled - the emptied container is simply discarded along with the rest of the consumed slot.
- EMI's recipe-tree system could plausibly drive *bulk* pattern creation from the Pattern Terminal once M6's recipe-viewer integration lands - explicitly future scope, not blocking this milestone.
- A caller with no specific face to offer `RequestFulfillment.request`'s own `deliverFace` (see "Delivery routing" above) still resolves via `TileRegistry.Hook`'s first-match-on-any-face fallback - two `PatternProviderHookType`/`TerminalHookType` hooks on different faces of one block are only genuinely disambiguated for callers that already resolved a specific face up front (a Crafting CPU job step, a terminal withdrawing to itself); a push-style delivery with no face in mind can still land on the wrong one of two same-type hooks sharing a block.
- **A Crafting CPU cluster's own topology is recomputed via BFS on every uncached lookup, not incrementally maintained** - fine at today's `MAX_CLUSTER_SIZE = 64` cap, but a much larger warehouse with many clusters churning placement/removal simultaneously could make this a real cost. TODO M5.
- **A busy cluster's own backlog has no starvation guard** - a steady stream of small jobs submitted to one cluster can keep a large job queued indefinitely behind them, since promotion is strict FIFO with no aging/priority. TODO M5.
- `CraftingBufferEncasementType.drainEverything` excludes routing back into this same member's own position but not every other member of the same cluster - a multi-member cluster could in principle drain a resource from one member's own storage into another member's, going nowhere, before a genuinely external route is found on a later tick. Rare in practice (the search prefers any reachable external destination first) but not structurally prevented.
